# План: что осталось до готовых программ

Документ отвечает на один вопрос: **что нужно сделать от сегодняшнего дерева до релиза 1.0
«Ярмарка»**. Майлстоуны и их состав определены в [ТЗ 8](../TASK.md), объём компонентов — в
[ТЗ 9](../TASK.md), приёмка — в [ТЗ 10](../TASK.md). Здесь только: где мы фактически, что нас
блокирует, в каком порядке делать и чем доказывается «сделано».

Оценка итерации в этом документе: **одна итерация = один цикл агента над одним компонентом**
(прочитали оригинал → парити-лист → логика + тесты → UI → smoke + скриншот → журнал, всё зелёное).
Калибруется на контрольной точке М0 (3.2): её бюджет 4 итерации и есть первая настоящая точка
отсчёта (ADR-0019). Все числа ниже до калибровки — **оценка из размеров ТЗ (S/M/L/XL), а не факт**.

**Риск №1 (0.4) — единственный, который может изменить план, а не расписание.** Под musl EFL 1.29.0
и Elementary не собирал никто: в Alpine есть только `efl` 1.28.1 в `testing`, собранный с `!check` и
`-Dnls=false`, а пакета Elementary с EFL-тулкитом нет вовсе. Ожидаемые классы правок: `dlopen`
модулей и динамическая musl, `iconv`/локали внутри EFL (в musl нет данных локалей), `realloc`/`strerror_r`
семантика, `SO_REUSEPORT`/`MSG_*` флаги, `__thread` и `secure_getenv`. Поэтому 0.4 идёт **до** любой
правки `crates/`, а результат — не «собралось/не собралось», а список патчей в `patches/efl-1.29.0/`
и запись в `docs/journal.md`. Не собралось с патчами ≤ 3 итераций → возвращаемся к владельцу с
выбором: `efl` 1.28.1 из `testing` (грозит расхождением с парити по 1.29) или отказ от musl для UI-стека.

## 3. Критический путь

```
диск → образ Alpine → musl-EFL+Elementary → композитор+скриншот → зеркала+парити
   → svetlitsa-efl (FFI) → svetlitsa-ui → izba/traktir/bukvar → starshina (композитор)
   → klyuchnik+domovoy+lavka+vestnik → smoke-сессия М2 → 8 программ М3 → 13 программ М4
   → novoselye+порталы+образ доставки → 1.0
```

Всё, что вне стрелок (темы, i18n, сайт, бенчи), — параллельные работы: они не разблокируют
следующий шаг, но без них релиз не принимается. Единственная ветка, где можно работать без
завершённого 0.4, — чистая логика без дисплея и без FFI (парсеры `traktir`, `uzelok-core`,
`svitok-core`, `vedro`, карта миграций): она пишется и тестируется на хосте, но **зелёной считается
только после прогона в контейнере** (3.8).

## 6. Что может сделать только владелец

1. **Диск (0.1).** Освободить ~10 ГиБ в Docker и решить, где живут 60 ГиБ. Агент чужие данные не удаляет.
2. **Пуш.** 46 коммитов ждут `git push`; теги канона (`canon-r*`) тоже.
3. **Q83 закрыт (21.11.2026): «ограничения сняты» — сборки на macOS допускаются.** Оформлено
   поправкой 1 к ADR-0023: инвариант переехал с хоста на образ (тот же Alpine-контейнер по digest'у),
   а рядом записан перечень проверок, которые на macOS не выполняются и не засчитываются (бенчи и RSS
   10.5, DRM/KMS и `libseat`, звук, сиды и питание, PAM+setuid, вотчеры поверх VirtioFS). От владельца
   здесь остаётся одна механическая вещь — **снять при первом прогоне числа с Mac** (`uname -m`,
   модель CPU, `sw_vers`, `df -k`, `docker info`, `uname -m` из контейнера): на Apple Silicon контейнер
   идёт через эмуляцию `amd64`, и тогда временем сборки нельзя ни пользоваться, ни аргументировать.
4. **Ревью парити-листов.** Вердикты «MVP / v1 / отложено» — решение человека (5, Q47–Q49); агент
   генерирует перечень и покрытие числом.
5. **Подпись канона.** Ключ в `canon/allowed_signers` принят вручную 15.11.2026; новые теги — только
   владелец.

## 8. Как считать прогресс (чтобы «готово» не стало мнением)

1. **Парити-лист закрыт** — у каждой позиции есть статус, у каждой строки перечня вердикт, MVP — «готово» (`xtask parity --check`).
2. **Ворота зелёные в контейнере** — `xtask ci`, включая `deps`, `licenses`, `parity`, `icons`, `canon`.
3. **Smoke пройден** — сценарий компонента под headless-композитором, код возврата 0.
4. **Скриншоты приложены** — 1024×768 и 1920×1080, «не серая тема» проверена механически.
5. **Запись в `docs/journal.md`** — что сделано, что отложено и почему.

Компонент, у которого выполнены 1–5, готов. Компонент, у которого «код есть, а smoke не гонялся»,
не готов ни в какой степени — это и есть причина, по которой М0 (среда) идёт до кода.
