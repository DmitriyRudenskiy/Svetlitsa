# ADR-0010: Механика линтов — наследование из `[workspace.lints]` без переопределений

Дата: 2026-11-15 · Статус: принято · Решения раундов 2–3 (Q22, Q25), ТЗ 3.1/6.3

## Контекст
ТЗ требовал `#![forbid(unsafe_code)]` везде, кроме FFI-крейтов, и «общие линты в `[workspace.lints]`».
Проверено на cargo 1.97.1:
- `[lints.clippy] workspace = true` → `error: invalid type: boolean 'true', expected a string or map`
  (поинструментное наследование не существует);
- `[lints] workspace = true` + любое своё значение линта → `error: cannot override 'workspace.lints' in
  'lints'` (переопределить нельзя **никак**, включая `unsafe_code = "allow"` в FFI-крейте).
То есть схема «все наследуют forbid, FFI-крейт переопределяет» невыполнима.

## Решение
- `[workspace.lints]`: `rust.unsafe_code = "forbid"`, `clippy.unwrap_used = "deny"`,
  `clippy.expect_used = "deny"`, `clippy.all = { level = "warn", priority = -1 }`.
- **`priority = -1` у группы `all` обязателен** (проверено на clippy 1.97): без него `all` и
  точечный `unwrap_used` получают одинаковый приоритет, и `clippy::lint_groups_priority` валит
  в красное каждый крейт workspace.
- Обычные крейты указывают **только** `[lints] workspace = true` и ничего не переопределяют.
- `svetlitsa-efl` и будущие `*-sys` наследование **не используют** и перечисляют линты явно
  (`unsafe_code = "allow"` + те же clippy-запреты) с комментарием, почему здесь `unsafe`.
- `xtask ci` сверяет множество крейтов вне наследования с allowlist; расширение allowlist — только ADR.
- `unwrap()`/`expect()` допускаются в `#[cfg(test)]` с `#[allow(clippy::unwrap_used, reason = …)]`
  и причиной — первый же собственный тест `xtask` на это и напоролся, то есть запрет работает.

## Последствия
- Обход запрета превращается в видимый дифф (крейт пропал из наследования), а не в тихий `#[allow]`.
- Минус: два списка линтов (workspace и явный) могут разъехаться; `xtask ci` обязан сверять и их.
