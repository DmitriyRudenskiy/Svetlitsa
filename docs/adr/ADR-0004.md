# ADR-0004: FFI-поверхность EFL — Elementary+Edje+Efreet+Eet, bindgen для широких заголовков

Дата: 2026-11-15 · Статус: принято · Решение раунда 1 (Q4), контрольная точка — ТЗ 3.2

## Контекст
В ТЗ был пункт «свой FFI-крейт, bindgen допускается точечно». Он не решал главного: какой объём EFL
вообще разрешён приложениям. `svetlitsa-efl` — единственный крейт с `unsafe` и единственная точка
падения всего проекта.

## Решение
Обязательная поверхность — **Elementary + Edje + Efreet + Eet** и минимум Eo/Ecore для жизненного цикла
объектов и событийного цикла. **Прямой Evas и Ecore_X из приложений — никогда** (только через
`svetlitsa-ui` / `svetlitsa-platform`). Bindgen — для широких заголовков (Eo, Evas, Elementary);
ручные `extern "C"` — для узких мест.

## Контрольная точка М0 (стоп-лосс)
До первой строчки компонентов спайк обязан пройти: окно Elementary из `svetlitsa-ui` под Xvfb +
Edje-макет темы + адаптер `Vec<T>` → Genlist item class + Eo-колбэк, приехавший в главный поток +
скриншот. Бюджет — **4 итерации** (итерация = один прогон `xtask ci`), счётчик в `docs/journal.md`.
На четвёртом неуспехе агент останавливается и пишет ADR «стоп-лосс» с планом Б: (1) форкать общинный
`efl` 0.3.0; (2) резать поверхность дальше — только Elementary-виджеты, отказ от Edje-макетов в пользу
кодовой сборки UI. Продолжать «ещё одной попыткой» без ADR запрещено.

## Последствия
- Поверхность, а не глубина, определяет объём FFI: сокращение поверхности дешевле, чем героическая
  обвязка всего EFL.
- Отказ от Edje-макетов — реальный план Б, а не угроза: он меняет тему «Лубок» с EDC-макетов на кодовую
  сборку и должен быть зафиксирован отдельным ADR, если будет выбран.
