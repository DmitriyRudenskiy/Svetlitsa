> **Назначение документа.** Это задание для локального агента-разработчика (Claude Code, aider, OpenCode, Codex CLI и т. п.). ## 1. Резюме проекта

**Проект:** «Светлица» (латиницей — `svetlitsa`) — рабочий стол с классической метафорой, собираемый с нуля на Rust поверх EFL, с сохранением идеологии MATE: классический двухпанельный десктоп, предсказуемость, низкие требования к железу, никаких «сюрпризов» в интерфейсе.

**Цель:** переписать все программные репозитории организации https://github.com/orgs/mate-desktop с языка C (GTK 2/3, GObject) на Rust (edition 2024; версия инструмента — пин из `rust-toolchain.toml`, 3.1), заменив GTK на EFL 1.29+ (Elementary/Evas/Edje), и выпустить сессию «Светлица» **только на Wayland** (ADR-0016): X11-сессии в 1.0 нет, композитор `starshina` — часть проекта (М2).

**Платформа и зависимости (решение владельца 21.11.2026):** «Светлица» — **только Wayland** и
**только PipeWire**. X11-сеанса, Xorg-сессии и X11-ветки портов в 1.0 нет (ADR-0016), XWayland не
поддерживается официально (ADR-0017), PulseAudio-стек не поддерживается (ADR-0022). Принцип «минимум
зависимостей» означает не «нулевой C», а **одну FFI-привязку на подсистему**: зависимость появляется
вместе с задачей, проверкой `LICENSE` и строкой в `docs/licenses.csv` (3.3, ADR-0002).

**Принцип «светлицы»:** светлица — светлая горница русской избы, где у каждого мастера своё ремесло и своё место, работа ведётся вскладчину, старшина ведёт работу, сходка решает споры, а результат один на всех. Компоненты «Светлицы» — это мастера, у каждого своё ремесло и своё имя (раздел 7). Имена — не украшение: это зафиксированные сущности проекта (имена крейтов, бинарей, D-Bus-сервисов и названий в UI).

**Объём (проверено через GitHub API, 15.11.2026):** в организации **46 репозиториев** — 45 кодовых плюс `.github`. Из 45 кодовых **не портируются и не имеют порта: 2** (`mate-desktop.org` — сайт, `mate-wiki` — вики). Карта раздела 2 покрывает 30 из них; судьба остальных 15 зафиксирована в **2.1**. Формулировка «28 репозиториев» из первой редакции была фактической ошибкой и исправлена.

**Что НЕ входит в задачу:** форки тем GTK, сохранение бинарной совместимости с плагинами C, поддержка GTK внутри «Светлицы» (gtk-rs запрещён как UI-слой, см. 6.6).

## 3. Технологический стек и ключевые решения

### 3.1 Язык и сборка

- **Rust, edition 2024.** Инструмент берётся **пакетами Alpine** из контейнера ворот (ADR-0023): `rust`, `cargo`, `rustfmt`, `rust-clippy`, `cargo-deny`, `sccache`; тройка `x86_64-alpine-linux-musl`, rustup в контейнере нет. `rust-toolchain.toml` (на старте — 1.97.1) означает **минимальную** версию и проверяется `xtask ci --doctor` по `rustc --version` внутри контейнера, а не устанавливает её. Архитектура одна — **x86_64**: 32-битных сборок и multilib нет, правило действует и для `svetlitsa-ext-*`. Термин «MSRV» из ТЗ убран: минимальный rustc = пин, поднимается **только вместе с ADR**. Внешнюю политику минимальных версий пакетировщикам не обещаем до М5 (PKGBUILD/deb — тогда отдельный ADR). Всё приложение-пространство — cargo workspace (монорепо `svetlitsa/`), а не 28 отдельных репозиториев: агенту проще держать атомарность изменений, а CI — целостность. Внутри workspace структура зеркальна карте из раздела 2 (`crates/izba`, `crates/lavka`, …), так что соответствие «репозиторий MATE → крейт» сохраняется.
- Служебная автоматизация — крейт `xtask` (сборка, пакеты, smoke-запуск, скриншоты). Meson/autotools не используются.
- Линт: `cargo fmt --check` + `cargo clippy --workspace --all-targets -- -D warnings` + `cargo deny` (лицензии, advisory) — все три исполняются только в среде ворот.
  «Только» значит, что там они обязательны и оцениваются; на машине разработки шаг исполняется,
  если инструмент установлен (с 2026-11-18 в `ci --local` исполняется и `deny` — Q81). Отсутствие
  инструмента — названный пропуск (Q57), но конфиг он не валидирует: нечитаемый `deny.toml` прожил
  так от раунда к раунду.
- **Механика запретов (проверено на cargo/clippy 1.97.1, ADR-0010).** В `[workspace.lints]`: `rust.unsafe_code = "forbid"`, `clippy.unwrap_used = "deny"`, `clippy.expect_used = "deny"`, `clippy.all = { level = "warn", priority = -1 }` (без `priority` группа `all` и точечный линт сталкиваются приоритетами, и `clippy::lint_groups_priority` валит каждый крейт). Обычные крейты указывают **только** `[lints] workspace = true` и **ничего не переопределяют** — cargo запрещает и переопределение (`cannot override \`workspace.lints\` in \`lints\``), и поинструментное наследование (`[lints.clippy] workspace = true` → `invalid type: boolean`). Единственные крейты вне наследования — `svetlitsa-efl` и будущие `*-sys`: они перечисляют линты **явно** (`unsafe_code = "allow"` + те же clippy-запреты) с комментарием, почему здесь `unsafe`. `xtask ci` сверяет множество крейтов вне наследования с allowlist; расширение allowlist — только через ADR. `unwrap()`/`expect()` допускаются в `#[cfg(test)]`-коде с атрибутом `#[allow]` и причиной.

### 3.2 Rust-биндинги EFL: стратегия FFI

Официальных Rust-биндингов EFL не существует. На crates.io есть только общинный крейт `efl` 0.3.0 (обновлён 12.07.2024, ~1.4 тыс. загрузок) — он устарел, не покрывает Elementary/Edje/Efreet и не является основой. **Решение: собственный крейт `svetlitsa-efl`.**

- **Сокращение поверхности (решение раунда 1).** Обязательная поверхность — **Elementary + Edje + Efreet + Eet** и минимум Eo/Ecore, необходимый для жизненного цикла объектов и событийного цикла. **Прямой Evas и Ecore_X из приложений — никогда** (только через `svetlitsa-ui` / `svetlitsa-platform`). Ручные `extern "C"` — для узких мест; **bindgen — для широких заголовков** (Eo, Evas, Elementary), потому что ручное объявление сотен сигнатур не читается и не проверяется.
- Слой 1 — `svetlitsa-efl/sys`: декларации против стабильного C API (Eo, Evas, Ecore, Ecore_Evas, Elementary, Edje, Efreet, Eet).
- Слой 2 — `svetlitsa-efl`: безопасные обёртки — владение `Eo*` через тип `EoHandle<T>` (Rust-владение + подсчёт ссылок Eo), колбэки через `+ 'static` замыкания с обёртками `extern "C"`, RAII для окон/объектов.
- Слой 3 — `svetlitsa-ui`: идиоматичные виджеты-композиты (Window, Dialog, ListView, Menu, Toolbar, FilePicker, StatusStrip) и загрузка темы «Лубок» (EDC). Именно его используют приложения; прямой доступ к `svetlitsa-efl` из приложений — только для отсутствующих виджетов и только с ADR.
- Правило совместимости: `svetlitsa-efl` целируется на **EFL ≥ 1.28**, разрабатывается на **1.29**; версия EFL в среде ворот проверяется `xtask ci --doctor` через pkg-config. Предупреждения об устаревших (deprecated) API EFL отслеживаются в воротах.
- **Контрольная точка М0 (стоп-лосс).** Прежде чем писать хоть строчку компонентов, спайк обязан пройти: окно Elementary из `svetlitsa-ui` под headless-композитором (`cage` или `weston --headless`, ADR-0016) + **Edje-макет темы** + **адаптер `Vec<T>` → Genlist item class** + **Eo-колбэк, приехавший в главный поток** + скриншот. Бюджет — **4 итерации** (определение итерации — 3.1/глоссарий), счётчик в `docs/journal.md`. На четвёртом неуспехе агент **обязан остановиться** и оформить ADR «стоп-лосс» с планом Б: (1) форкать общинный `efl` 0.3.0 и добивать поверхность в нём; (2) резать поверхность дальше (только Elementary-виджеты, отказ от Edje-макетов в пользу кодовой сборки UI). Продолжать «ещё одной попыткой» без ADR запрещено.

### 3.3 Что остаётся на C (белый список «гостинцев»)

MATE живёт в экосистеме GLib. Полный уход от C-зависимостей — долгий путь; на старт фиксируем честный allowlist (расширение — только через ADR):

| Зависимость | Зачем | Как используем | План ухода |
|---|---|---|---|
| **GIO/GVFS (glib)** | VFS: сеть, корзина, монтирование (критично для амбара/бересты) | FFI через `gio-sys`-подобный sys-крейт; только слой данных, не UI | свой крейт `svetlitsa-vfs` (сначала поверх FUSE/GVfs D-Bus) |
| **libdconf (чтение)** | миграция настроек пользователей MATE | разовый импорт при первом запуске компонента | после М4 — родной бэкенд |
| **poppler (poppler-glib)** | PDF в свитке | `poppler-rs` (gir-биндинги), слой данных | нет — poppler остаётся |
| **libarchive / p7zip** | форматы архивов узелка | sys-FFI | частично заменить крейтами `tar`/`zip` |
| **PipeWire** | звук в граммофоне, регулятор громкости, потоки | **одна** FFI-привязка: `libpipewire` или сокет `pipewire-pulse` — выбор за задачей 6.11, ADR-0022 | нет — PipeWire + WirePlumber остаётся |
| **Efreet + Eet (из EFL)** | XDG-меню, .desktop, иконки, конфиги | это часть EFL, используется через svetlitsa-efl | меню — pure Rust (traktir v2) |

Запрещено тянуть: GTK2/3 и gtk-rs (UI), libwnck (роль — композитор `starshina`, ADR-0019), libsoup (заменяется reqwest), libgtop (заменяется procfs), gtkmm. С 21.11.2026 в этом же списке — **любые X11-крейты** (`x11rb`, `x11`, `xcb`: ADR-0016) и **вторая звуковая привязка** (`libpulse-binding`, `pulseaudio`: ADR-0022).

### 3.4 Конфигурация и данные

- Хранилище: `svetlitsa-config` — типизированные схемы настроек на serde, бэкенд Eet (через svetlitsa-efl) + JSON-файлы в `$XDG_CONFIG_HOME/svetlitsa/`. Схемы версионируются, миграции — кодом.
- **Совместимость с MATE:** при первом запуске компонент ищет `/org/mate/...`-ключи в dconf (чтение через `dconf dump` или FFI libdconf) и импортирует их по карте соответствия `crates/<имя>/migrate/`. Карты — код + тесты **только на фикстурах дампа** (`tests/fixtures/mate-dconf/*.dump`, словарь). Фикстуры снимаются `scripts/fixtures/capture-mate-dump.sh` **на госте среды ворот — Ubuntu MATE 24.04 LTS** (тот же образ, что и для сборки, отдельная «одноразовая машина» не нужна); задача на М0/М1, потому что без неё «миграция работает» в DoD — непроверяемая формальность.
- **Порядок дня 1 (фикстура до сборок):** подъём → клон/снапшот нетронутого образа → capture (`dconf dump /org/mate/`, `~/.config`, версии пакетов) → и только потом EFL и эксперименты. Любой прогон компонента может писать dconf-ключи, а загрязнённая фикстура навсегда мигрирует мусор в канон.
- **Происхождение фикстуры обязательно:** рядом с дампом в `tests/fixtures/mate-dconf/` — id образа, его дата и вывод `dpkg-query` по пакетам MATE. Фикстура без происхождения — то же «почти зелёное» (ADR-0006).
- Никакой бинарной совместимости с GSettings-схемами MATE не требуется (пользовательская миграция — импортом).

### 3.5 D-Bus

- Клиент и сервер — крейт `zbus` (pure Rust; **tokio в workspace не вводится**). Исполнитель zbus живёт **в отдельном потоке**, а не на цикле Ecore; в главный поток события приходят через **один** публичный примитив переноса из `svetlitsa-efl` (обёртка над `ecore_main_loop_thread_safe_call`). Модель целиком — 4.3, ADR-0005. Eldbus из EFL не используется.
- Системные имена сервисов «Светлицы» — префикс `org.svetlitsa.*`; **обязательные совместимые интерфейсы** (чтобы не сломать экосистему и сторонние клиенты):
  - vestnik → `org.freedesktop.Notifications`;
  - stavni → `org.freedesktop.ScreenSaver`;
  - klyuchnik → shim-интерфейс `org.gnome.SessionManager` (достаточный для logout/reboot-клиентов) + собственный `org.svetlitsa.Session`;
  - kerosinka → клиент `org.freedesktop.UPower` и `org.freedesktop.login1`;
  - lavka → статус-трей: `org.kde.StatusNotifierItem`/`StatusNotifierWatcher` через zbus. XEmbed-хоста нет (ADR-0016): протокол поднимает окно на X11, а X11-сеанса в 1.0 нет.

### 3.6 Wayland

- **Wayland — единственная платформа, с первой итерации и до 1.0 (ADR-0016, решение владельца 21.11.2026).**
  X11-сеанса, Xorg-сессии и X11-ветки портов в 1.0 нет. Обязательная поверхность EFL — Elementary +
  Edje + Efreet + Eet на бэкенде **Ecore_Wl2** (3.2); приложения к X11 не обращаются и не могут.
- **Композитор — наш и он в М2 (ADR-0019):** `starshina` на фреймворке **smithay** (pure Rust),
  `novoselye` — сеанс поверх него. На Wayland «менеджер окон» и композитор — один процесс, поэтому
  ADR-0007 («свой композитор после 1.0») пересмотрен: откладывать композитор — значит откладывать
  саму возможность показать окно.
- **Чем заменяется X11-механика** (полная таблица — ADR-0016): EWMH → протоколы сеанса и `xdg_toplevel`
  + собственный `org.svetlitsa.Session`; XEmbed-трей → `org.kde.StatusNotifierItem` + `zwlr`-слой;
  `xkbcomp`/`setxkbmap` → модель раскладок композитора на `xkbcommon`; RandR → `wp-output-manager`/
  `xdg-output` + `wlr-output-management`; DPMS и удержание от сна → собственный слой сидов поверх `seatd` (ADR-0023: `systemd-inhibit` в образе нет);
  `_NET_ACTIVE_WINDOW` → `xdg_activation`; снимок окна → собственный путь захвата композитора.
- **XWayland не поддерживается официально (ADR-0017):** он не запрещён и не удаляется, но не входит
  ни в один DoD, ни в одну сборку сеанса. Флаг в `starshina` остаётся как инструмент отладки.
  Следствие, зафиксированное честно: X11-приложения (в том числе старые MATE-апплеты) в сеансе
  «Светлицы» гарантированно не работают.
- **Что это отменяет в тексте ТЗ.** Все упоминания X11 означают **механизм оригинала MATE**, а не
  задачу порта; в 1.0 не исполняется ничего из того, что требует X-событий. Омонимия названий
  («трей», «раскладка», «блокировка экрана») закрывается ссылкой на ADR-0016, а не новой правкой.
- **Что это даёт сверх отмены:** глобальные горячие клавиши, оверлейные слои, индикатор раскладки,
  менеджер буфера обмена и снимок экрана становятся возможными — их в MATE держал композитор,
  которым мы владеем сами.

### 3.7 Прочая инфраструктура

- Локализация: `gettext-rs`; каталоги **`po/<бинарь>.po`** (один домен на бинарь, Q37); `ru` — конвертация из `po/ru.po` зеркал MATE скриптом на М1 (лицензии GPL/LGPL совместимы), `en` — исходные строки в коде. Покрытие: **fuzzy-строки считаются непокрытыми** (`msgfmt --check` + сверка с выгрузкой `xgettext`), иначе «покрытие» становится резиной (ТЗ 12.9). **Локаль не из libc (ADR-0023):** в musl нет данных локалей, а `iconv` урезан, поэтому имена месяцев и дней недели, «вчера/сегодня» и порядок сортировки берутся из таблиц на Rust (`icu` или собственных), перекодирование — только `encoding_rs`; `strftime` с `%B`/`%A`, `strcoll` и `iconv` запрещены воротами.
- Логирование: `tracing` с записью в **журнал сеанса** — JSONL в `$XDG_STATE_HOME/svetlitsa/log/<сеанс>/`. `tracing-journald` не используется: journald в образе нет (ADR-0023), а `letopis` v1 читает именно журнал сеанса (9.20).
- Ошибки: `thiserror` в библиотеках, `anyhow` в бинарях; паников в прод-путях нет (`catch_unwind` на границе колбэков svetlitsa-efl).
- Тесты без дисплея — логика (парсеры, меню, конфиги, схемы); тесты с дисплеем — **headless-композитор** (`cage`/`weston --headless`, раздел 10, ADR-0016). `Xvfb` в воротах не используется.
- Ворота: fmt/clippy/test/deny/deps/build одним прогоном `xtask ci` в среде ворот (3.8, 6.3); `deps` — запрет X11-стекки и второго звукового слоя (ADR-0016, ADR-0022); ночное задание «толока» — полная сборка workspace + оба smoke + скриншоты + RSS-прогоны (раздел 10). Удалённого CI пока нет (ADR-0006).

### 3.8 Среда ворот (где всё это исполняется)

Факт, проверенный 15.11.2026 (снимок среды до ADR-0023): сборочная машина `192.168.0.86` — **bare metal, Pop!_OS 24.04 LTS, x86_64** (`systemd-detect-virt` → `none`), 16 ядер, 46 ГБ RAM, **не QEMU-VM** (первая редакция ТЗ ошибалась), Rust нет вообще, `meson`/`ninja` нет, `git`/`rsync`/`make`/`Xvfb` есть, сеть наружу есть. Факт, проверенный 21.11.2026: `192.168.0.86` отвечает на ping (0% потерь, 1.19 мс); `192.168.0.80` — Gentoo, x86_64, docker 28.0.4 работает, `/var/lib/docker` занят на 91% (19 ГиБ свободно). Среда ворот — **контейнер на Alpine** (ADR-0023), какой хост его носит — Q80.

- **Хост ворот — `192.168.0.80` (Q82 закрыт владельцем 21.11.2026: «на машине Gentoo»); хостом сборки может быть и macOS (Q83 закрыт в тот же день: «ограничения сняты»).** Проверено на `.80`: Gentoo, x86_64, 16 ядер, 62 ГБ RAM (49 доступно), Docker 28.0.4 работает. Инвариант — **образ, а не хост**: один и тот же Alpine-контейнер по digest'у, поэтому «собралось на Mac» и «собралось на Gentoo» — один и тот же прогон, а перечень проверок, которые macOS дать не может (бенчи, RSS, DRM/KMS, звук, сиды, PAM, вотчеры), закрытым текстом лежит в ADR-0023 «Поправка 1» и помечается в артефактах прогона. Среда ворот — контейнер на Alpine в этом Docker (ADR-0023), а не QEMU/KVM-VM в облаке (решение Q40 отменено тем же ADR). «.86» остаётся **исключённой совсем**, и не «на время»: диск заполнен на 100% (переснято 15.11.2026: **2.8 ГБ свободно из 460**), это чужая работающая машина, а освобождать там 60 ГБ означало бы удалять чужие данные. Нестабильное основание под воротами хуже, чем никакого. macOS исключён (см. ниже). **Правило подмены:** если появится третья локальная машина, она становится средой ворот немедленно (бесплатно, локально, ночные прогоны не считаются по часам) — одна запись в `docs/journal.md`, образ переезжает без изменений.
- **Критерий готовности среды — не `df`, а зелёный `xtask ci --doctor` внутри контейнера.** До него контрольная точка М0 (4 итерации, 3.2) не начинается; её статус — **«ожидает среду»**, путь фиксирован, действие = собрать образ и прислать вывод doctor'а целиком. **Дисковый бюджет — требование, а не пожелание:** нужно ≥ 60 ГиБ свободного места (образ тулчейна с C-замыканием, `/opt/svetlitsa-efl`, `target/`, `sccache`), а на хосте ворот на 21.11.2026 свободно **19 ГиБ из 206** при 10.4 ГиБ формально освобождаемых в Docker; расчёт и порядок действий — [`docs/roadmap.md`](docs/roadmap.md), раздел 2. Бюджета нет — статус М0 остаётся «ожидает среду», имитации работы не разводим.
- **Гость контейнера — Alpine (ADR-0023), а не Ubuntu MATE (Q44 отменён).** Следствие, которого не было в Q44: **фикстуры дампов MATE (3.4) в воротах не снимаются** — в образе нет ни dconf, ни самих MATE-пакетов. Их снимают на любой машине с MATE (одноразовый контейнер `ubuntu:24.04` + `mate-*`, либо живая система) и **коммитят** в `tests/fixtures/mate-dconf/`; ворота работают по коммиту, а не по живой MATE-системе.
- **Golden image + manifest (Q45, ADR-0013):** в первый день скрипты пишутся в контейнере и прогоняются, после зелёного `xtask ci --doctor` снимается образ со средой (EFL 1.29.0 + Elementary под musl, тулчейн, зеркала), рядом — manifest (**digest базового образа Alpine**, sha256 тарбóлов, версии Alpine-пакетов тулчейна, путь к `/opt/svetlitsa-efl`, sha зеркал). Дальнейшие подъёмы — из образа, `doctor` при каждом подъёме.
- **Чек-лист требований среды — [`docs/env-checklist.md`](env-checklist.md)** (Q43): пакеты, версии EFL, диск, дисплей, доступ к зеркалам. Это единственная заготовка, которую можно писать до появления среды; скрипты — нет.
- **Скрипты среды (`scripts/efl-build.sh`, `scripts/build-in-docker.sh`) вслепую не пишутся** — по тому же принципу, что и CI-файлы без раннера (ADR-0006): непрогнанный скрипт это «почти зелёное». Они пишутся и сразу прогоняются в первый день внутри контейнера на хосте ворот, в журнал идёт реальный вывод. Проверено на себе (21.11.2026): `efl-build.sh` был написан, смонтирован и запущен, напечатал «ГОТОВО» — и не собрал ничего, потому что каждая команда в нём обёрнута в `… | tee -a "$LOG"`, а `pipefail` в BusyBox ash нет: статус возврата meson теряется. Правило работает — вывод скрипта воротам не верят, верят `pkg-config` и `readelf`.
- **Красные ворота от нехватки RAM или места — проблема среды, а не кода.** Их нельзя «починить» правкой теста; они останавливают итерацию и идут в `docs/journal.md`.
- **EFL берётся из релизного тарбóла 1.29.0** (Elementary входит в то же дерево EFL, отдельного
  релизного тарбóла Elementary-как-тулкита нет), а не из пакетов: в Alpine `efl` — только 1.28.1 и
  только в `testing`, собранный с `!check` и `-Dnls=false`, а пакета `elementary` (EFL-тулкит) нет
  вовсе (индекс edge, 21.11.2026). Значит musl-сборка 1.29.0 — наша: свой скрипт, свои патчи, свои
  включённые тесты и NLS (ADR-0023). Сборка — `scripts/efl-build.sh`: пин версии + sha256 + установка
  в `/opt/svetlitsa-efl`, `PKG_CONFIG_PATH` задаёт скрипт окружения; версия проверяется
  `xtask ci --doctor`.
- **Rust** — пакеты Alpine (`rust`, `cargo`, `rustfmt`, `rust-clippy`), rustup в контейнере нет (ADR-0023); `sccache` обязателен (общая машина, дорогие линковки).
- **Зеркала `vendor/mate/`** — shallow-клоны 43 кодовых репозиториев: **995 МБ** (проверено 15.11.2026 скриптом `scripts/fetch-vendor.sh`; из них 191 МБ — `.git`). Оценка «300–400 МБ» первой редакции была занижена втрое: `--depth 1` экономит историю, а не файлы. Для сравнения: полные `.git` всех 46 реп — 1.36 ГБ, из них 599 МБ — сайт. Зеркала держат на машине с дисковым бюджетом; `docs/licenses.csv` генерируется по ним и **коммитится** (3.9).
- **Канон и поток работ (переснято 21.11.2026):** `origin` — **`git@github.com:DmitriyRudenskiy/Svetlitsa.git`** (проверено `git remote -v`); план «голый репозиторий `~/git/svetlitsa.git` на .86» первой редакции не используется — на диске .86 его держать нельзя. Рабочее дерево живёт на хосте ворот, контейнер получает его **bind-монтированием локального диска** и возвращает `artifacts/` в то же дерево. **sshfs и прочие сетевые монтирования запрещены**: FFI-сборка поверх сетевого ФС даёт неповторимые падения. Пуш и любые правки истории — за владельцем (агент коммитит, не пушит). **Резервная копия истории — сам `origin`**: пуш после каждой закрытой итерации (иначе вся история впереди `origin` живёт на одном диске хоста), а «голый репозиторий рядом со средой ворот» из первой редакции не используется — на диске `.86` под него нет места.
- **macOS — хост сборки, но не источник всех доказательств (Q83, поправка 1 к ADR-0023).** Homebrew не используется в принципе: Elementary там не пакуется, `efl` 1.29.0 пришлось бы собирать руками — тулчейн и C-замыкание живут в Alpine-контейнере, как и на Linux-хосте. Что на macOS **не считается** доказательством: замеры 10.5 (гипервизор и эмуляция `amd64`), RSS-прогон (память гостевой VM), вывод на экран через DRM/KMS и `libseat` (`/dev/dri` не проброшен), звук PipeWire, сиды и питание (`seatd`/UPower/`backlight`/`hwmon`), PAM+setuid `stavni-auth`, а вотчеры файлов флакают из-за `inotify` поверх VirtioFS. При первом прогоне на Mac в журнал идут `uname -m`, модель CPU, `sw_vers`, `df -k`, `docker info` и вывод `uname -m` из контейнера: от архитектуры зависит, считается ли время сборки вообще.

### 3.9 Лицензии (их раньше не было — это была дыра)

Порты — производные работы GPL-кода MATE, поэтому лицензия определяется сверху вниз по upstream, **пофайлово**, а не одной строкой на проект (ADR-0002):

| Группа | Лицензия | Примеры и основание |
|---|---|---|
| Порты приложений MATE | **GPL-2.0-or-later** | marco→starshina, mate-panel→lavka, caja→ambar, pluma→beresta и большинство остальных |
| Порты `mate-terminal`, `mate-netbook` | **GPL-3.0-or-later** | `morzyanka`, `lezanka`: upstream-COPYING — GPL-3 |
| Порты `mozo`, `libmateweather` | **LGPL-2.1-or-later** | `bufetchik`, `vedro` |
| Ядра, портирующие библиотечные части | **LGPL-2.0-or-later** (не GPL!) | `izba`←`libmate-desktop`, `traktir`←`mate-menus`, `ambar-core`←`libcaja-extension` — в upstream есть `COPYING.LIB` |
| Инфраструктура «Светлицы» | **MIT OR Apache-2.0** | `svetlitsa-efl`, `-ui`, `-config`, `-dbus`, `-platform`, `-xdg`, `-vfs`, `xtask` |
| `caja` | **микс** | `COPYING` GPL-2 + `COPYING.LIB` LGPL-2 + `COPYING.EXTENSIONS`: разбирается по подкаталогам |

- Механика: `xtask licenses` генерирует **`docs/licenses.csv`** из `vendor/mate/*` (COPYING + заголовки исходников) на Mac, CSV коммитится. В воротах `xtask ci` проверяется **сам CSV**: он есть, схема читается, каждый крейт workspace в нём упомянут, и его лицензия совместима с зависимостями (cargo-deny). Заново генерировать — вручную, при смене зеркал.
- Формулировка «-or-later» подтверждается заголовками файлов (`libcaja-extension`: «either version 2 of the License, or (at your option) any later version»).

**Git-процесс монорепозитория** (все проекты — в одном репо `svetlitsa`; «структура» — дерево выше):

- **Ветки:** `feat/<майлстоун>/<имя-компонента>` (6.1), а также `fix/…`, `docs/…`; `main` — защищённая, изменения только через PR; один компонент — одна ветка и один PR.
- **Коммиты:** `<тип>(<крейт>): суть` — типы `feat`, `fix`, `refactor`, `test`, `docs`, `chore` (пример: `feat(lavka): SNI-хост трея`); история `main` линейная (squash-merge).

Удалённый репозиторий уже есть, рабочего раннера для среды ворот — нет, workflow появится вместе с ним (ADR-0006).
- **`origin`** — **`git@github.com:DmitriyRudenskiy/Svetlitsa.git`** (переснято 21.11.2026, `git remote -v`): общая точка пуша обоих исполнителей. План первой редакции («голый репозиторий `~/git/svetlitsa.git` на сборочной машине») не используется — на диске хоста под него нет места (3.8), а историю от потери диска защищает пуш в `origin` после каждой закрытой итерации.
- **Шаблон PR** — форма отчёта 6.10; PR без прогонов `xtask ci` в описании не сливается.
- **Версии:** все крейты меняются синхронно (`0.x.y` до 1.0); релиз = тег `v1.0.0` + запись в `CHANGELOG.md` + кодовое имя из 7.4.
- **Не коммитятся:** `vendor/mate/` (зеркала качает `scripts/fetch-vendor.sh`), `artifacts/` (скриншоты идут в артефакты CI и в описание PR), `target/`.

### 4.3 Модель событий и потоков

- **Два потока, один владелец UI.** Главный поток — цикл Ecore: все UI-колбэки живут только в нём. Исполнитель zbus — в **отдельном потоке**; из него в главный всё приходит через единственный публичный примитив переноса (`svetlitsa-efl`, обёртка над `ecore_main_loop_thread_safe_call`). Прямых `async`-вызовов из UI-кода нет, блокирующего I/O на Ecore-потоке нет (6.4). ADR-0005.
- **Демоны без окон (`domovoy`, `kerosinka`) — вообще без Ecore**: только поток zbus. Ecore подключается там, где есть окно (`vestnik`, `stavni`) или где нужен таймер UI.
- Композитор starshina — собственный цикл на smithay (события Wayland-сеанса), UI-диалоги — отдельный процесс на svetlitsa-ui, связь по zbus. X-сокета и X-цикла в архитектуре нет (ADR-0016).

## 5. Поток работы агента над одним компонентом (жизненный цикл порта)

1. **Чтение оригинала.** Клонировать shallow-зеркало исходника в `vendor/mate/<repo>` (read-only, не включать в workspace). Составить парити-лист `docs/parity/<имя>.md` в **двух уровнях** (9 решения раунда 1): **модули и фичи — обязательно для всех компонентов**; **пофункционально — только публичный API библиотечных крейтов** (`izba`, `traktir`, `bukvar`, `vedro`, `uzelok-core`, `ambar-core`, `svitok-core`). Требование «полный список функций C-версии» для `caja`/`marco`/`mate-panel` — это тысячи функций, и его буквальное исполнение либо парализует работу, либо превращает парити-лист в фикцию (что запрещено 6.4). Функциональный слой — это **публичная поверхность**, а не все C-функции репозитория (Q48): генератор берёт заголовки, которые билд-система объявила публичными (`install_headers` / `*_HEADERS`; если билд-система ничего не перечисляет — каталог без `private`, и лист это пишет), вырезает комментарии и export-макросы и собирает объявления нестатических функций; многострочный прототип — одно объявление. Статические функции, макросы и `typedef` — не поверхность. Если оригинал не устанавливает заголовков (engrampa), функционального C-прототипа нет — поверхность ведётся руками.
Список модулей генерируется из зеркал (`xtask parity [крейт]`), чтобы честность была механической; лист двухслойный (Q47): генерируемый блок (отпечаток зеркала + дерево модулей + публичные функции) перезаписывается, рукописный блок вердиктов — нет. **Лист обязан быть непротиворечивым** (Q49), а не «полным»: каждая позиция имеет статус и пометку MVP/v1/отложено; каждая строка перечня имеет вердикт; отложенное перечислено с причиной; **нулевой лист обязан содержать непустые «Причина:» и «Переносится:»** — пустой перечень без объяснения есть притворство, а не парити. **Лист закрыт, когда каждая позиция имеет статус и каждая строка перечня — вердикт; MVP-позиции — «готово».** Ворота `xtask parity --check` (шаг `parity` в `xtask ci`) красны, если: листа нет; отпечаток зеркала не совпал; лист правился вне генератора; лист закрыт при неполном покрытии вердиктами; нулевой лист без объяснения. Покрытие открытого листа печатается числом и красным не является — вердикт остаётся работой человека. Каждая позиция помечается **MVP / v1 / отложено**, где MVP — прогоняемый smoke-сценарий компонента из раздела 9 (не доля строк и не на усмотрение агента).
2. **ADR-заготовка.** Зафиксировать: какие фичи в итерации, какие C-зависимости нужны, какие D-Bus-интерфейсы и конфиг-ключи появляются.
3. **Данные, потом UI.** Сначала логика (парсеры, конфиги, D-Bus) с тестами без дисплея; затем окна на svetlitsa-ui по таблице 4.4.
4. **Миграция.** Если у C-версии есть GSettings-ключи — карта миграции `crates/<имя>/migrate/` + тест на дампе.
5. **Приёмка.** Прогон DoD (6.9), smoke-скриншоты (10), обновление TASK-журнала `docs/journal.md` (что сделано, что отложено).
6. **Отчёт** (форма — 6.10).

## 6. Правила работы агента (контракт)

### 6.1 Порядок
- Работать строго по майлстоунам (раздел 8); внутри майлстоуна — по одному компоненту за раз; ветка `feat/<майлстоун>/<имя-компонента>`. Никогда не смешивать два компонента в одной ветке/PR.
- Git-соглашения монорепо — 4.2: коммиты `<тип>(<крейт>): суть`, PR в защищённую `main` (шаблон — 6.10), релизы тегируются `v1.x.y` с записью в `CHANGELOG.md`.
- Майлстоун считается закрытым, только когда закрыты все его компоненты и общий smoke сессии проходит (10.4).
- Не переписывать порядок без ADR с обоснованием.

### 6.2 Самостоятельность
- Уточняющих вопросов по обычным делам не задавать (локальный агент работает автономно). Любое неочевидное решение — ADR; конфликт с этим ТЗ — тоже ADR с пометкой «расхождение с ТЗ».
- **Правило эскалации (исключение из автономности).** Агент **обязан остановиться и спросить**, если решение относится к одному из четырёх классов: (1) влияет на безопасность — `stavni`/PAM, монтирование, права, файловые операции с чужими данными; (2) возможно повреждение пользовательских данных — миграция настроек, массовые файловые операции `ambar`; (3) труднообратимо и меняет контракт — имя крейта/бинаря, D-Bus-интерфейс, формат конфига, лицензия; (4) расхождение с ТЗ касается состава майлстоуна или DoD. Во всех остальных случаях — ADR и работаем дальше. Молча изобретать вместо вопроса запрещено: проект на годы, и выдуманный ответ возвращается через десятки компонентов.
- При пробеле в знаниях о MATE — читать исходник в `vendor/mate/`; при пробеле о EFL — читать заголовки установленных библиотек EFL и официальную документацию enlightenment.org. Не выдумывать API.

### 6.3 Качество (блокирующие ворота)

Все ворота исполняются **только одним прогоном `xtask ci` в среде ворот** (3.8); «зелёным» считается только прогнанное там.

- `xtask ci --doctor` — окружение: версия rustc = пин, EFL/Elementary по pkg-config, **Wayland-композитор и `wayland-scanner` вместо `Xvfb`** (ADR-0016), свободное место; падение doctor'а останавливает итерацию до сборки (нехватка RAM/места — проблема среды, 3.8);
- `cargo fmt --check` — 0 замечаний;
- `cargo clippy --workspace --all-targets -- -D warnings` — 0;
- `cargo test --workspace` — зелёный;
- `cargo deny check` — 0 (лицензии/дубликаты/advisory) + проверка `docs/licenses.csv` (3.9);
- линты-запреты из `[workspace.lints]` (3.1, ADR-0010) работают, и множество крейтов вне наследования совпадает с allowlist (`svetlitsa-efl`, `*-sys`);
- `xtask parity` — листы парити против текущего отпечатка зеркала (5); шаг не зеленеет, когда
  сверять нечего (раунд 11, Q79): пустая карта, отсутствующее зеркало целиком и пропущенная
  строка карты красны, а пропуск назван именем репозитория;
- `xtask icons --check` — закрытый список имён (ADR-0012) сверяется с зеркалом **в обе
  стороны**: лишнее имя и отсутствующее имя красны одинаково, а отсутствие зеркала — красная
  строка, а не пропуск (раунд 10, Q57): зелёный цвет от нечего проверять — не доказательство;
- `xtask canon` — реестр канона сверяется **в обе стороны**: запись ↔ тег (Q54), а каждая
  запись обязана проходить `git verify-tag` по принципу из `identity` и записанного в
  каноне `canon/allowed_signers` (Q58): помеченное состояние проверяемо, а не доверено.
  Ключ подписи **отдельный** от ключа пуша; **якорь доверия — `canon/allowed_signers` в
  проверяемом дереве** (первый ключ принят вручную: 15.11.2026, Mac; проверка не требует
  настроек клона именно поэтому — нет файла в дереве, нет и вердикта, и это отдельная
  красная строка, а не «принципал не тот»).

  **Четыре случая сверки (Q59)**, все относительно проверяемого состояния `S` (тег
  разыменован до sha коммита; «строго предшествует» = предок `S` и не равен `S`):

  1. запись в реестре есть, тег **не** строгий предок `S` → краснота «реестр зовёт
     чужеродный тег»; реестр, зовущий тег с другой линии, болен тем же, что тег без записи;
  2. запись есть, sha тега расходится с записью → краснота, немедленно;
  3. записи нет, тег — строгий предок `S` → краснота «тег есть, записи в реестре нет»;
  4. записи нет, тег равен `S` или лежит вне линии → строка **«вне сверки»**, не краснота.
     Строка печатается всегда: молчание означало бы, что тег ушёл из сверки незаметно.

  Собственный тег состояния записан быть не может: дерево не содержит собственный sha — вот
  настоящая причина, почему наивная двусторонняя сверка не имела ни одного удовлетворения.
  Цена правила: тег на HEAD без записи ловится ближайшим следующим коммитом; расхождение
  sha ловится немедленно, случаем 2. **Правило действует с коммита, который его ввёл;
  прежние деревья отвечают собственными воротами** — сегодняшним бинарником на старом дереве
  получается другой вердикт, и выдавать его за вердикт дерева нельзя (раунд 9, свип).
- **Смена ключа канона (Q58), окно перекрытия.** (1) Новый ключ дописывается в
  `canon/allowed_signers` и в реестр записью с датой, машиной и тем, кто принял; (2) старый
  ключ живёт до следующего канон-тега; (3) следующий канон-тег подписан новым ключом;
  (4) старый ключ **помечается выведенным, но остаётся в файле** — ворота проверяют
  подпись каждой записи, и удаление старого ключа перекрасило бы прежние записи в красный,
  то есть подделало бы историю задним числом. Смена ключа без записанной до неё процедуры —
  красные ворота.
- новые C-зависимости — только из allowlist 3.3 и только с ADR.

**Ворота, которые нельзя показать в среде ворот, не считаются** (Q57): если шаг нельзя
запустить там (нет среды, нет ключа), он обязан быть отделяемым (`xtask ci --local`
вычёркивает только `doctor`), а его отсутствие в прогоне — названо в отчёте. Серые
«сделано» от прошлой итерации — то же самое: не прогнанный сегодня негатив не считается
проверенным никогда.

**Зелёный цвет от нечего проверять — не доказательство** (Q79, раунд 11): шаг ворот обязан
краснеть, когда сверять нечего — пустая карта, отсутствующее зеркало, пропущенная строка
перечня. Отсутствие входа — красная строка, называющая причину, а не `continue`: молчаливый
пропуск неотличим от успешной проверки, и именно так ворота зеленеют, ничего не проверив.

**Правило негатива** (Q53): структурное правило, внесённое в ворота итерацией, обязано в
той же итерации показать два прогона — красное состояние (правило нарушено намеренно) и
зелёное (восстановлено), с выводом в журнале. Красный прогон без зелёного = правило не
проверено. Постоянный негатив-тест — минимум, но беглый прогон руками обязателен, потому
что тест проверяет правило, а не свой вывод.

**Тестовый уровень правила негатива (Q53):** тест ворот валиден, только если сломанное
правило его краснит: временно отключи правило — тест обязан стать красным. Тест, который
не краснеет от сломанного правила, — пересказ, а не тест. Тест предиката или хелпера
таковым быть может, но проверкой правила не считается и в зачёт итерации не идёт.

**Корень проверяемого дерева спрашивают у git (Q62).** `xtask` живёт внутри репозитория,
поэтому контекст сборки совпадает с корнем и подмена невидима: бинарник, собранный из
одного дерева, судил его же, будучи запущенным из чужого checkout, — и печатал зелёное
про состояние, к проверяемому дереву не относящееся. Путь берётся из
`git rev-parse --show-toplevel` в каталоге прогона. Постоянный тест поднимает временный
git-каталог с поддельным `canon.toml` и краснеет на возврат к `CARGO_MANIFEST_DIR`.

**Ротация ключа имеет исполняемую половину (Q63).** Запись реестра несёт необязательное
поле `key` — принципал, подписавший именно её; без поля действует тогдашний `identity`.
Выведенный ключ помечается комментарием в `canon/allowed_signers`, но из файла не
удаляется: удаление перекрасило бы красным все записи старше ротации. Ворота красны,
если **последний** канон-тег подписан не действующим `identity` — иначе ротация
проверялась бы только в день ротации, а тег, подписанный выведенным ключом, проходил бы
вечно.

**Мутация, ничего не покраснившая, — не мутация, а намерение (Q60).** В журнал идёт вывод
прогона, а не замысел: «смутировал и откатил» без строки `FAILED` не считается. Таблица
соответствия — обязательная часть журнала итерации; по ней видно, кому краснеть, и ловит
тест-обманку по месту.

### 6.3.1 Числа в документах (Q61)

Каждое число в журнале и документах живёт только с командой, которая его печатает, и с
коммитом, на котором команда снята. **Число по памяти — не факт.** Строки не стираются:
устаревшее число помечается ссылкой на команду, которая его сняла, а не удаляется. Число
без указанной команды — кандидат на пометку «не проверено», как это случилось с «1336»
(раунд 9, см. журнал).

## 7. Брендинг: почему «Светлица»

### 7.1 Смысл имени
Светлица — светлая горница русской избы: парадная комната, где светло, чисто и собрано всё лучшее, — там работали, рукодельничали и принимали гостей. Имя объединяет обоих родителей проекта: **свет** — прямой наследник Enlightenment (Enlightenment Foundation Libraries, EFL — «просветление»), а **мята** — привет MATE: пучки мяты сушили как раз в таких горницах, и мятный настой — тот самый травяной «mate», от которого родительский рабочий стол получил имя. Заодно светлица — точная метафора рабочего стола: светлая горница дома, в которой трудятся мастера-компоненты (старшина, ключник, домовой, лавка…), где всё под рукой и где светло, а не тёмно и запутанно. Народная линия сохраняется: «помочи» и «толока» — совместная работа «всем миром», что и есть дух свободного ПО. Слоган проекта: **«Всем светло»**. Второй слоган, для упаковки релизов: **«Мята и свет»**. Отклонённые варианты имени (зафиксированы, чтобы не всплывали повторно; решение — тогдашний ADR-0001, текст в `docs/journal-1-3.md`, приложение А): **Терем** — образ множества окон и ярусов хорош, но не держит связь с мятным родом MATE; **Лад** — точнее как принцип, чем как имя: система должна жить «в ладу» с пользователем и железом (память без гонок и паник — это и есть лад), поэтому слово уходит в ценности проекта, а не в название; **Сплав** — слияние MATE и Enlightenment через Rust передано верно, но безлично.

### 7.2 Система имён (фиксирована, менять только через ADR)

Ядро и «двор»: изба (библиотека-основа), лавка (панель), амбар (файлы), сходка (настройки), ключник (сеанс), домовой (демон настроек), старшина (оконный менеджер), ставни (хранитель экрана), новоселье (Wayland).
Ремесленные приложения: береста (текст), свиток (документы), вернисаж (картинки), счёты (калькулятор), морзянка (терминал), узелок (архив), граммофон (звук), буфетчик (редактор меню).
Мелкая утварь светлицы: шкатулка (скриншот дагеротип, поиск сыщик, журналы летопись), самоделки (апплеты), барометр (датчики), лежанка (нетбук-режим), пристройки (расширения амбара), вестник (уведомления), керосинка (питание), дозор (монитор системы), трактир (меню-спека), букварь (клавиатура), вёдро (погода).

Эстетика — народные промыслы и ремесло: тема «Лубок», резьба «Наличники», звуки «Колокольчики», обои «Пейзажи» (палитры: хохлома, гжель, мезень). Маска/маскот — **конёк** (конёк крыши избы: резной деревянный конёк — традиционный знак завершённого дома; логотип — силуэт конька на коньке крыши). Имена бинарей/крейтов/D-Bus — латиницей (транслитер из 7.2/раздела 2): `izba`, `lavka`, `ambar`, … D-Bus: `org.svetlitsa.*`. Имена в UI и документации — русские.

### 7.3 Тема «Лубок»
- EDC-тема Elementary: резные наличники-рамки у окон, палитры «Хохлома» (тёмная: чёрно-красно-золотая), «Гжель» (светлая: бело-синяя), «Мезень» (контрастная, для слабовидящих — повышенный контраст и крупные шрифты).
- Иконки: монохромный лубочный контур + цветные заливки; имена — по freedesktop-спеке. Геометрия — ремесленная (ромб, солярные знаки, косые линии прялки), без китча и фотореализма; контур и заливка — отдельные слои, чтобы иконки читались и в монохроме.
- Шрифты: PT Sans/PT Serif (свободная русская типографическая пара) с фолбэком на DejaVu. (Точный комплект шрифтов фиксируется ADR, дистрибутивно-нейтрально.) В Alpine пакетов `font-pt-*`/`paratype` нет (индекс edge, 21.11.2026), поэтому комплект лежит в репозитории под OFL, фолбэк — `font-dejavu`.
- Звуковая тема «Колокольчики»: вход в сеанс, уведомление вестника, ошибка.
- Анимации: пружинная физика (spring) для раскрытия меню и пузырей вестника; длительность и амплитуда — параметры темы, в палитре «Мезень» анимации отключаются (доступность важнее украшения).
- Базовые тона — «природные» (тёмно-зелёный, охра, береста, морёный дуб): фоны, выделение, акценты поверх палитр выше; точные значения — в EDC-переменных темы, не в коде.
- **Объём темы к М2 (Q36):** все Elementary-виджеты, которые к М2 используют лавка/ставни/диалоги; обе базовые палитры — «Гжель» и «Хохлома»; декор «Наличники» для starshina. «Мезень» — после стабилизации двух базовых.
- **Закрытые списки, а не «всё»:** список виджетов М2 и список иконок живут в парити-листе `svetlitsa-ui` (`docs/parity/svetlitsa-ui.md`), пополняются PR'ом, а не молча. `xtask icons` генерирует список иконок из зеркала `mate-icon-theme` — по freedesktop-именам, реально используемым М2-компонентами. **Копия у списка одна** (ADR-0014): приложение читает его тем же кодом, чем ворота сверяют, — `svetlitsa-icons` встраивает лист и разбирает генерируемый блок; генерируемого Rust-файла и переноса руками нет.
- **Доступность уровня 1.0 (обещание, а не намерение):** полная навигация с клавиатуры (включая диалоги и `stavni`), контраст и крупные шрифты палитры «Мезень», отключаемые анимации, масштабируемые шрифты. **Скринридеры (AT-SPI) в 1.0 не входят** (12.8) — в EFL их нет, и обещать их было бы обещанием несуществующего.

### 7.4 Релизы
- Версии: календарно-семантические `1.x.y`; кодовые имена релизов — русские ярмарки и праздники: `Ярмарка` (1.0), `Масленица`, `Кузьминки`, `Капустница`…
- Ночная сборка — «толока» (совместная работа: все компоненты собираются и прогоняются вместе).

## 9. По-репозиторные спецификации

Формат каждого пункта: **Был** (что в MATE) → **Задача** → **Ключевые решения** → **Риски** → **DoD** (сверх общего 6.9). Порядок пунктов соответствует порядку исполнения в майлстоунах.

### 9.1 mate-desktop → «Изба» (izba) — М1, L
- **Был:** базовая библиотека MATE: API фонов рабочего стола, миниатюры (thumbnailer по XDG), диалог «О программе», хелперы RandR/мониторов, общие утилиты.
- **Задача:** библиотека-основа «Светлицы»: типы общих настроек (вместе с svetlitsa-config), генерация миниатюр по спецификации freedesktop (кэш `~/.cache/thumbnails` совместим), «О программе» (композит svetlitsa-ui), фоны (хранение, смена, режимы заливки; отрисовка фона выполняет лавка/домовой), RandR-хелперы над svetlitsa-platform.
- **Решения:** миниатюры — своя реализация спеки (pure Rust, загрузчики Evas + `image`); «О программе» читает данные из `about.toml` в корне workspace.
- **Риски:** RandR-тонкости (многомониторные профили) — частично отложено в v1 (ADR).
- **DoD:** izba генерирует совместимые с MATE/GNOME миниатюры (проверка на реальном кэше), окно «О программе» рендерится, izba не тянет GTK.

### 9.2 mate-menus → «Трактир» (traktir) — М1, M
- **Был:** библиотека спецификации меню freedesktop.org: парсинг .menu-файлов, merge-правила, дерево приложений, legacy-флаги.
- **Задача:** v1 — обёртка Efreet-меню через svetlitsa-efl (быстро и совместимо); v2 (усадьба) — pure Rust-парсер .menu (merge/OnlyShowIn/NotOnlyShowIn/каталоги) с полным тестовым прогоном на файлах спеки; структуры данных и API не меняются между v1/v2 (за trait-границей `MenuSource`).
- **Решения:** модель дерева — иерархия `MenuNode` (serde-friendly) для кэша; потребители — лавка, буфетчик, сходка.
- **Риски:** тонкости merge-алгоритма спеки; поэтому v2 допускается только после дифф-теста против Efreet на 20+ реальных .menu.
- **DoD:** на дампе `mate-applications.menu` v1 и v2 дают идентичные деревья (дифф-тест), буфетчик редактирует и сохраняет валидный .menu.

### 9.3 libmatekbd → «Букварь» (bukvar) — М1, M
- **Был:** библиотека клавиатуры: конфигурация раскладок/опций, индикатор, применение через xkb.
- **Задача:** модель раскладок (список, опции, переключение) на `xkbcommon`-крейте. **Применяет их композитор:** `bukvar` собирает `xkb_keymap` и отдаёт его `starshina`, дальше композитор сам ставит карту каждому `xdg_surface`; `xkbcomp`, xkb-extension и `setxkbmap`-эквивалентов в коде нет (ADR-0016). Индикатор-виджет для самоделок (текст + флаг-иконка, рисование на Evas) получает активную раскладку от композитора по протоколу сеанса.
- **Решения:** применение настроек — единственный модуль (клиенты: domovoy, skhodka, индикатор); хранилище — svetlitsa-config (`keyboard.toml`), миграция из `/org/mate/peripherals/keyboard/`.
- **Риски:** xkb-опций мир велик; MVP — group switch (alt+shift и т.п.), grp_led, типичные опции; остальное — отложено с ADR.
- **DoD:** под headless-композитором переключение раскладок меняет состояние ввода активного окна (проверка через протокол сеанса, а не чтением X-свойств), индикатор рисует метку раскладки; опция group switch (alt+shift) работает как привязка композитора.

### 9.4 marco → «Старшина» (starshina) — М2, XL (итерациями)
- **Был:** оконный менеджер (форк metacity): ICCCM/EWMH, фокус, placement, рамки/кнопки, рабочие столы, Alt+Tab, темы marco, клавиатурные привязки, мин/макс/на весь экран.
- **Задача:** **композитор Wayland на smithay** (на Wayland композитор и менеджер окон — один процесс,
  ADR-0019). Обязанности: `xdg-shell` (`xdg_toplevel`/`xdg_popup`) + `xdg-decoration` для клиентов без
  своих рамок; placement, фокус, move/resize, максимизация, fullscreen; рабочие столы — `ext-workspace-v1`
  либо собственный интерфейс (решение фиксируется в ADR, список клиентов для лавки идёт через
  `org.svetlitsa.Session`); глобальные клавиатурные привязки; `wlr-layer-shell` (панель, обои, оверлеи);
  `ext-idle-notify-v1` и `ext-session-lock-v1` (ставни); `zwlr-data-control` (памятка); `wp-viewer`/
  `xdg-output` (выводы); снимок экрана — собственный путь захвата. Декорации окон — Edje-группы темы
  «Наличники»; Alt+Tab-переключатель — окно svetlitsa-ui; конфиг привязок — svetlitsa-config
  (`starshina.toml`), миграция из `/org/mate/marco/`.
- **Чем не занимается:** EWMH/ICCCM-клиентами (X-клиентов в сеансе нет), XWayland (флаг сборки есть,
  DoD нет — ADR-0017), композитингом-«ради теней» (v2).
- **Решения:** UI-диалоги (запрос подтверждения выхода и пр.) — отдельный процесс `starshina-dialog` на svetlitsa-ui, связь по zbus `org.svetlitsa.WM`; композитинг (тени/прозрачность) — v2, отложено (ADR). Режим «печной кладки» — v2 (ADR): опциональный тайлинг — плотная подгонка окон блоками (snap-to-grid + полуавтоматическая раскладка), не заменяет классический флоатинг, включается в настройках окон сходки.
- **Риски:** самый дорогой компонент всего проекта и первый, чего в MATE-порте раньше не было: М2 держится на нём целиком. Совместимость проверяется против EFL-клиентов на `Ecore_Wl2` (в первую очередь `morzyanka` и demo-окно), а не против EWMH-клиентов; темы marco не переносятся (backlog: парсер marco-тем — ADR). Оценка `XL` дана до переезда композитора в М2 — уточняется после итерации (а).
- **DoD:** smoke под headless-композитором: 3 окна разных классов — фокус/перемещение/ресайз/макс/мин/закрытие с клавиатуры; список окон читает лавка через `org.svetlitsa.Session`; Alt+Tab работает; сеанс живёт 10 минут без утечек (проверка RSS в скрипте).

### 9.5 mate-session-manager → «Ключник» (klyuchnik) — М2, M
- **Был:** менеджер сеанса: запуск/завершение, автозапуск XDG, экран выхода, клиентский реестр (форк gnome-session).
- **Задача:** демон: порядок запуска компонентов Светлицы (из `session.toml`: starshina → domovoy → lavka → vestnik → …), автозапуск XDG-файлов через svetlitsa-xdg, экран выхода/завершения (svetlitsa-ui), shim `org.gnome.SessionManager` (Setenv, Logout, Shutdown) + `org.svetlitsa.Session` (полный API), ингибиция (задержки завершения) — через собственный слой сидов, а не через logind (ADR-0023).
- **Решения:** журнал сеанса — tracing; «сохранить сеанс» v1 — список запущенных .desktop (совместимо по духу с MATE).
- **MVP по COSMIC (9.30):** объём сеанса = четыре заботы их ключника — что запускать, автозапуск, доступность, владелец сеанса: у них — в logind, у нас — в своём слое (1 026 строк как нижняя граница). «Сохранить сеанс» целиком — вне MVP.
- **Риски:** гонки автозапуска — фиксированный порядок + повтор; зависимость от собственного слоя сидов (ADR-0023): `logind` и `systemctl` в образе нет, прямого вызова чужого демона не планируется.
- **Секрет-агент сеанса (решение владельца 21.11.2026, ADR-0020):** ключник — владелец
  `org.freedesktop.NetworkManager.SecretAgent`: регистрируется на системной шине, получает запрос
  секрета от демона (новая точка подключения / изменённый пароль), поднимает окно пароля на
  svetlitsa-ui, сохраняет секрет в каталог сеанса (`0700`, файл `0600`). polkit-агент не поднимается:
  вместо чужого фреймворка политик — один D-Bus-интерфейс. Отказ пользователя — `CancelGetSecrets`
  и честная ошибка «не подключено», а не тихий повтор. Секреты не попадают в `svetlitsa-config`,
  в историю буфера (`pamyatka`) и в журналы (`tracing` пишет факт запроса, не значение).
- **DoD:** smoke-сессия стартует по `klyuchnik start`, выход по D-Bus гасит компоненты в обратном порядке, сеанс завершается кодом 0 под headless-композитором.

### 9.6 mate-settings-daemon → «Домовой» (domovoy) — М2, M
- **Был:** демон настроек: клавиатура/мышь/раскладки, фон, медиа-клавиши, доступность, плагины.
- **Задача:** демон на zbus `org.svetlitsa.Settings`: подписка на svetlitsa-config-изменения и
  применение: раскладки (модель из `bukvar` передаётся композитору), фон (через `izba` — обои рисует
  слой `background` композитора, «корня X» нет), медиа-клавиши (привязки регистрирует композитор,
  домовой переадресует громкость в граммофон, яркость — в керосинку), хранитель (организация вызова
  ставней по `ext-idle-notify-v1`), мышь/тачпад (параметры libinput — собственный конфиг-модуль;
  `xinput`-эквивалента нет).
- **Решения:** домовой — плагинов по MATE-модели не создаёт: один демон с внутренними trait-модулями; каждый модуль — отдельный unit-тест.
- **MVP по COSMIC (9.30):** интерфейс домового — varlink по образцу их settings-daemon (вместо D-Bus-фасада); varlink — кандидат в зависимости по ADR-0002. Поверхность остаётся наша: мышь, тачпад, раскладка — у них этих модулей нет.
- **XSETTINGS → наш конфиг (ADR-0016):** X11-механизм XSETTINGS (тема, шрифт, курсор для GTK-клиентов) не переносится. Тема и шрифт читаются приложениями «Светлицы» из `svetlitsa-config`, а тема EFL грузится Edje-макетом «Лубок»; для сторонних клиентов тема — часть темы композитора (`xdg-desktop-portal` `Settings`, М5).
- **Риски:** применение раскладок зависит от того, что композитор уже принимает `xkb_keymap`, — то есть домовой в М2 проверяется только вместе со starshina; тестировать на реальных изменениях под headless-композитором.
- **DoD:** изменение ключа конфига через D-Bus применяется в сеансе (раскладка, фон, медиа-клавиша) — все три сценария в smoke под headless-композитором.

### 9.7 mate-panel → «Лавка» (lavka) — М2, XL (итерациями)
- **Был:** панель (верх/низ, доп. панели): апплеты, список окон, трей, меню приложений, «выполнить», свойства панели.
- **Задача:** панель на svetlitsa-ui: позиции (top/bottom/left/right, много панелей), зоны: меню приложений (на traktir), лаунчеры (.desktop через svetlitsa-xdg), список окон (через `org.svetlitsa.Session`, данные от starshina), трей (**только SNI-хост** `org.kde.StatusNotifierItem`/`StatusNotifierWatcher` через zbus), часы (композит); реестр апплетов в-процессе (`AppletFactory` trait, см. самоделки); диалог «выполнить» (Alt+F2); конфиг панелей — svetlitsa-config (`lavka.toml`), миграция раскладки панелей MATE (маппинг `/org/mate/panel/` → lavka.toml).
- **Решения:** апплеты v1 — в-процессе крейты (безопасно для агента, без ABI-проблем); внешние апплеты по D-Bus — v2 (ADR). «Выполнить» ищет через traktir + PATH.
- **MVP по COSMIC (9.30):** апплет = отдельный процесс с токеном (их модель панели), а не крейт в-процессе; конфиг панели = профиль + якорь + список `entries`; размер — контракт `suggested_size`/`suggested_padding`. Риск: то, ради чего выбирались in-процесс-апплеты (отсутствие ABI-границы), придётся держать протоколом.
- **Трей (12.13, переписано 21.11.2026):** 1.0 = **SNI-хост и ничего кроме**. XEmbed-хоста нет: он
  поднимает чужое X-окно, а X-сеанса в 1.0 нет (ADR-0016). Следствие записано в 12.x как ограничение:
  X11-приложение, умеющее только XEmbed, в трей не встанет.
- **Панель — слой композитора:** лавка висит на `wlr-layer-shell` (слой `panel`), и это не внешний
  риск: композитор наш (`starshina`, ADR-0019), протокол входит в его DoD М2. Контракт размера —
  `suggested_size`/`suggested_padding` (9.30, конфликт 3), а не «как в MATE 24px».
- **Демо-клиент окон** (тестовый бинарь: открывает N `xdg_toplevel`, регистрируется SNI-агентом) — общий артефакт для smoke-прогона трея и для RSS-сценария «толоки» (10.5). Делается в М2 вместе с лавкой, не «когда-нибудь».
- **Риски:** SNI покрывает не всех (часть приложений рисует иконки через устаревшие варианты протокола); тестировать с demo-клиентом и реальными клиентами; старый конфиг MATE с 3+ панелями — тест-дампы.
- **DoD:** smoke под headless-композитором: панель с меню, часами, списком окон и треем; demo-трей-клиент отображается; Alt+F2 запускает gedit-подобное приложение (исп. `xdg-open`-эквивалент).

### 9.8 mate-notification-daemon → «Вестник» (vestnik) — М2, S
- **Был:** демон уведомлений: org.freedesktop.Notifications, пузыри, темы, причины закрытия.
- **Задача:** полная реализация `org.freedesktop.Notifications` (Notify, Close, GetCapabilities — body/images/actions, GetServerInformation); рендер пузырей на svetlitsa-ui (Edje-макет «Лубок»), очередь, не беспокоить (режим), экран настройки v1 — конфиг-файл.
- **Решения:** уведомления не перехватываются от MATE — это свой сервер; совместимость: демон регистрирует имя `org.freedesktop.Notifications` на сессионной шине.
- **MVP по COSMIC (9.30):** граница из трёх крейтов — демон / хранилище истории / конфиг (у них три отдельных пакета), а не один крейт `vestnik`.
- **Риски:** мало; обязательный тест против `notify-send` (с картинкой и действиями).
- **DoD:** notify-send с action и image — пузырь отображается, действие срабатывает, Close гасит.

### 9.9 pluma → «Береста» (beresta) — М3, M
- **Был:** текстовый редактор (форк gedit 2): вкладки, поиск/замена, подсветка (gtksourceview), кодировки, печать, плагины.

### 9.11 mate-terminal → «Морзянка» (morzyanka) — М3, M

### 9.12 mate-system-monitor → «Дозор» (dozor) — М3, M
- **Был:** монитор процессов/ресурсов (gtkmm + libgtop): процессы, CPU, память, сеть, диски, kill.
- **Задача:** процессы — `procfs`-крейт (+/proc + /sys), графики CPU/память/сеть — собственный виджет Plot на Evas (данные ring-buffer), файловые системы — statfs через rustix, kill/signals — rustix; сортировка/фильтры, дерево процессов, «убить/остановить/продолжить» с подтверждением.

- **MVP по COSMIC (9.30):** источник метрик — `sysinfo` (+ `nvml-wrapper` для GPU), а не свой обход `/proc`; оба кандидата по ADR-0002. Их же разбивка «источник / график / таблица процессов» — каркас и для multiload-апплета.
- **Риски:** поля libgtop ≠ /proc напрямую — парити-лист по столбцам; права (kill чужих) — ошибки обрабатывать.
- **DoD:** smoke: kill процесса из UI работает, графики обновляются, фильтр по имени.

### 9.14 engrampa → «Узелок» (uzelok) — М3, M
- **Был:** архиватор (форк file-roller): создание/распаковка tar/zip/7z/rar и др., частичная распаковка, шифрование zip.
- **Задача:** ядро `uzelok-core`: trait `Archive` + реализации: tar/gz/bz2/xz/zst (`tar`+`flate2`/`bzip2`/`zstd`), zip (`zip`, с шифрованием), 7z/rar — libarchive/p7zip FFI (чтение; запись 7z — по ADR); UI на svetlitsa-ui: дерево архива (Genlist), извлечение выборочно, создание с опциями, интеграция с амбаром (контекстное меню — через D-Bus контракт).

### 9.15 mate-media → «Граммофон» (gramofon) — М3, S
- **Был:** регулятор громкости/медиа (форк pulseaudio-gvc): микшер, устройства, апплет.
- **Задача:** микшер **на PipeWire**: устройства вывода/ввода, уровни по приложениям, выбор устройства по умолчанию, mute; UI-окно + компактный апплет для лавки (слайдер+меню); клавиатурные громкость-клавиши — привязки композитора, переадресация от домового.
- **Решения (план перевёрнут 21.11.2026, ADR-0022):** **v1 — сразу PipeWire**, PulseAudio-стек не
  поддерживается вовсе, отдельного «слоя v1» нет. **Одна** привязка на выбор: (а) `libpipewire` —
  нативный клиент, но уровни по приложениям придётся брать из графа PipeWire; (б) сокет
  `pipewire-pulse` (pulse-совместимый протокол) — даёт «приложение ↔ поток ↔ уровень» готовым, ценой
  зависимости от включённого pulse-модуля в WirePlumber. Выбор фиксируется ADR до первой строки
  микшера; вторая привязка запрещена воротами (тот же принцип, что и одна привязка на подсистему в 3.3).
- **Риски:** поведение микшера тонкое (устройства исчезают во время прогона, потоки в `creating`);
  тесты — с demo-источником на реальном PipeWire/WirePlumber, mock по протоколу не проверяет ничего.
- **DoD:** громкость/mute/устройство меняются и читаются обратно тем же клиентом, которым писались
  (`wpctl`/`pw-cli` — только как независимая сверка в smoke), апплет показывает уровень; при
  отсутствующем PipeWire — явная ошибка «звук недоступен», а не молчаливый ноль.

### 9.16 mate-utils → «Шкатулка» (shkatulka) — М3–М4, M
- **Был:** набор утилит: mate-screenshot, mate-search-tool, mate-logview.
- **Задача:** три бинаря:
    - **dagerotip** — снимок экрана: полный экран/окно/область (собственный путь захвата `starshina`: запрос кадра композитору; выбор области — оверлей-слой `overlay`, XShape нет; там же — портал `Screenshot`, М5), задержка, сохранение (PNG/JPEG) + диалог папки; интеграция с вестником (уведомление «снимок сохранён»).
  - **syschik** — поиск файлов: walkdir + regex + glob, фильтры (размер/дата/тип), результаты Genlist, «открыть в амбаре/бересте» (контракт D-Bus).
  - **letopis** — просмотр журналов: v1 — **только собственные журналы компонентов** (`tracing` → JSONL в каталоге сеанса), фильтры, live-tail; системных журналов в 1.0 нет — ни `journalctl`, ни парсера syslog (ADR-0023).
- **Решения:** общая UI-библиотека (шкатулка-common) для диалогов.
- **Риски:** захват окна, которого композитор уже не видит (свёрнуто/на другом столе), — отдельный случай с явной ошибкой; прав на чужие журналы не требуется, потому что системных журналов в 1.0 нет (ADR-0023).
- **DoD:** три сценария smoke: снимок сохранён и корректен (размер >0), поиск находит тестовый файл, журнал фильтруется.

### 9.17 caja → «Амбар» (ambar) — М4, XL (несколько итераций, ключевой компонент)
- **Был:** файловый менеджер (форк Nautilus 2): иконки/список/компакт, VFS (GIO/GVFS), корзина, монтирование, миниатюры, закладки, emblems, поиск, свойства, десктоп-иконки, пакетное переименование, боковая панель.
- **Задача:** ядро `ambar-core`: VFS — svetlitsa-vfs (GIO-FFI: файлы/корзина/монтирование/сеть через GVFS-mounts), модель папок с инкрементальным сканированием (inotify через `inotify`-крейт), mime-действия (через svetlitsa-xdg + Efreet), миниатюры — изба; UI: три вида (Genlist/Gengrid), боковая панель (места/устройства/закладки/сеть), вкладки, адресная строка (кнопки+ввод), свойства, корзина (восстановление), поиск (встроенный + вызов сыщика), пакетное переименование v2; рабочий стол (десктоп-иконки) — отдельный процесс `ambar-desktop` (ADR).
- **Решения:** все операции с файлами — фоновые задачи с прогрессом в UI; расширенные атрибуты — xattr через rustix.
- **MVP по COSMIC (9.30):** плагинов в 1.0 нет — их файловый менеджер (27 681 строка) работает без них вообще. Трейт `SvetlitsaExt` — post-MVP.
- **Риски:** самый большой UI-компонент; GVFS-FFI сложен (маршалы GFileInfo) — sys-крейт с тестами на каждый метод; не забывать про права и симлинки.
- **DoD:** сценарии smoke: копирование 1000 файлов с прогрессом, корзина+восстановление, монтирование demo-образа (loop), миниатюры картинок, закладка, mime-открытие берестой/вернисажем/узелком.

### 9.18 caja-extensions → «Пристройки» (pristroyki) — М4, S
- **Был:** расширения Caja: open-terminal, sendto, image-converter, wallpaper, xattr-tags.
- **Задача:** trait `SvetlitsaExt` (контекст: выделение, папка, меню) в ambar-core; крейты-расширения в-процессе: «открыть в морзянке», «отправить в…» (mail/disk/сеть — v1: локальные цели), «конвертировать изображения» (вызов вернисажа-функций), «сделать фоном» (D-Bus domovoy), «xattr-теги».
- **Решения:** реестр расширений — feature-флаги ambar; внешний ABI не обещаем (ADR).
- **MVP по COSMIC (9.30):** расширение = отдельный процесс, каталогов поиска три (их pop-launcher), падение расширения не роняет амбар. Реестр feature-флагом — post-MVP.
- **Риски:** мало; главное — интерфейс расширения стабильный с первого дня.
- **DoD:** каждое расширение демонстрируется в smoke-меню амбара.

### 9.19 atril → «Свиток» (svitok) — М4, M→L
- **Был:** просмотр документов (форк evince): backends poppler/djvu/tiff/ps/dvi/pixbuf/comics, оглавление, поиск, презентация, печать.
- **Задача:** ядро `svitok-core`: trait `DocumentBackend`; бекенды: PDF — `poppler-rs` (gir; glib — data-слой по allowlist 3.3), DjVu — djvulibre FFI (v2), TIFF — `tiff`-крейт, comics — uzelok-core (cbz/cbr→zip/rar), pixbuf — image; UI: непрерывная прокрутка страниц (Evas-объекты страниц), масштаб по ширине, оглавление/индексы (из poppler), поиск по документу (poppler find), презентация (fullscreen); печать — вне 1.0 (12.12).
- **Решения:** рендер страниц — offscreen-буфер → Evas Image; кэш страниц по кругу.
- **Риски:** poppler-rs gir-биндинги требуют glib-окружение — изолировать в svitok-pdf крейте; цветопрофили не переносим (ADR).
- **DoD:** PDF-тест (гиперссылки, формы v2), поиск находит текст, оглавление переходит к разделу, комикс cbz открывается.

### 9.20 mate-control-center → «Сходка» (skhodka) — М4, M
- **Был:** центр управления: модули настроек (фон, внешний вид, клавиатура, мышь, окна, дата-время и др.).
- **Задача:** оболочка-окно с категориями (Genlist слева), модули = композиты из крейтов компонентов: фон (izba), раскладки (bukvar), окна (starshina-конфиг), панель (lavka), уведомления (vestnik), питание (kerosinka), дата-время (timedatectl/zbus), пользователи v2. Каждый модуль — отдельный крейт `skhodka-<модуль>`, чтобы компонент мог показать свой блок настроек и без сходки.
- **Решения:** модули регистрируются в реестре сходки; сходка не знает деталей — только контракты виджетов.
- **MVP по COSMIC (9.30):** модуль настроек = страница из секций с двусторонней привязкой к конфигу, отдельный крейт на страницу (их граница `page`). Реестр сходки живёт над этой границей.
- **v1-модули сходки (зафиксированы, Q35):** `appearance`→izba, `display`→izba/RandR, `keyboard`→bukvar, `mouse`→domovoy, `windows` и `keybindings`→starshina, `system-info`→izba («О программе»). В upstream `mate-control-center/capplets` **12 модулей** (проверено по зеркалу; `common` — инфраструктура, не модуль), остальные пять — v2: `accessibility`, `about-me`, `default-applications`, `time-admin` (хватает кнопки `timedatectl`), `network`.
- **Правило недублирования:** настройки панели, уведомлений и питания — **не модули сходки**; они живут в собственных диалогах лавки, вестника и керосинки, сходка их не копирует (иначе два места правят одно состояние).
- **Риски:** широта; объём фиксируется списком выше и парити-листом.
- **DoD:** изменение фона/раскладки/поведения окон из сходки применяется немедленно (smoke).

### 9.21 mate-power-manager → «Керосинка» (kerosinka) — М4, M
- **Был:** управление питанием (форк gnome-power-manager): батарея/уровень, яркость, сон/гиббернация, inhibit, уведомления.
- **Задача:** демон на zbus: UPower-клиент (уровень/статус), собственный слой сидов поверх `seatd` (сон/hibernate/inhibit-сессии; logind в образе нет — ADR-0023), яркость — /sys/class/backlight (+dconf-совместимость не нужна), таймауты простоя → вызов ставней; апплет-иконка лавки (самоделки-композит), события → вестник; диалог «низкая батарея».
- **Решения:** ингибиция морзянки/свитка при просмотре — D-Bus-контракт `org.svetlitsa.Power.Inhibit`.
- **Риски:** вариативность железа (backlight-пути); тесты — с mock-системой через trait.
- **Связь с композитором:** `ext-session-lock-v1` и `ext-idle-notify-v1` входят в DoD `starshina` (М2) — ставни М4 опираются на готовый протокол, и это надо проверить в М2, а не обнаруживать в М4.
- **DoD:** smoke с mock-UPower: уровень меняется → иконка/уведомление обновляются, яркость применяется.

### 9.22 mate-screensaver → «Ставни» (stavni) — М4, M
- **Был:** хранитель/блокировщик (форк gnome-screensaver): гашение, блокировка с PAM, мониторинг активности.
- **Задача (переписана 21.11.2026, решение владельца):** это компонент про **заботу**, а не про
  XScreenSaver-extension. Три обязанности:
  1. **Политика бездействия:** таймауты (бездействие → гашение → блокировка) берутся из
     `svetlitsa-config`, источник бездействия — `ext-idle-notify-v1` у композитора; пользователь может
     выключить блокировку совсем, и это должно быть видно в UI, а не «где-то в конфиге».
  2. **Состояние «заблокировано до пароля»:** блокировка — `ext-session-lock-v1` (композитор сам
     отрезает ввод и рисует наш слой), а не «окно поверх всех». Пока блокировка активна, ни одно окно
     не принимает ввод и ни один скриншот не показывает содержимое; это проверяется smoke-сценарием.
  3. **Пробуждение по событию:** движение мыши/клавиша снимают гашение, `Lock`/`Unlock` от `klyuchnik` (не от logind — ADR-0023)
     (сон/пробуждение) переводят состояние, а не дублируют его; совместимый интерфейс
     `org.freedesktop.ScreenSaver` (Lock, SimulateUserActivity, GetActive) остаётся для клиентов,
     «заблокировать» — из меню лавки.
  Аутентификация — **отдельный setuid-root хелпер `stavni-auth`** (ADR-0009): минимальная поверхность —
  `pam_authenticate` + `pam_close_session`, конфиги через него не читаются.
- **Решения:** гашение экрана — `ext-idle-notify-v1` + управление выводом (`wlr-output-management`/DPMS на стороне композитора), не клиентский DPMS; темы хранителей v1 — простые Evas-анимации (2–3: «угли», «занавес», «пейзаж»), старые xscreensaver-хаки не поддерживаются (ADR).
- **MVP по COSMIC (9.30):** ключ ингибирования принадлежит сессии, а не процессу — ингибирование переживает перезапуск приложения (их idle, 751 строка).
- **Риски:** безопасность блокировки — обязательный ревью: нельзя обойти Tab/Alt+F2 (отладка в smoke со вторым клиентом).
- **DoD:** простой 10 минут → гашение; Lock → без пароля не выйти (проверка обходов), SimulateUserActivity снимает.

### 9.23 mate-applets → «Самоделки» (samodelki) — М4, M
- **Был:** набор апплетов панели (форк gnome-applets): часы, список окон, переключатель столов, multiload, индикатор раскладки, диски, командная кнопка, записки, погода, fish и др.
- **Задача:** реестр апплетов лавки (`AppletFactory` + `Applet` traits: виджет, конфиг, меню); v1-набор: **часы** (цифровые/аналоговые — Evas-рисование, календарь по клику), **список окон** (данные `starshina` через `org.svetlitsa.Session`), **переключатель столов**, **multiload** (графики CPU/сеть/память — dozor-данные), **индикатор раскладки** (bukvar + состояние у композитора), **ярлыки дисков** (ambar-vfs mounts), **командная кнопка** (строка+иконка), **листочки** (записки, v1 — файлы), **погодный апплет** (вёдро), **рыбка** (пасхалка: аквариум-виджет с фразами классиков — тексты из открытых источников, ADR на список). v2: invest-статистика (отложено — API меняются, ADR).
- **Решения:** апплет = крейт `samodelki-<имя>`, подключается feature-флагом в лавку.
- **MVP по COSMIC (9.30):** как в 9.7 — апплет отдельным процессом; их перечень наполнения панели (19 апплет-крейтов) — план минимума.
- **Риски:** у каждого апплета свой источник данных — trait-контракты на данные (ClockSource, LoadSource…), чтобы лавка не завязывалась на конкретику.
- **DoD:** все v1-апплеты в smoke-лавке; каждый с конфигом и миграцией из `/org/mate/panel/applets/` (где применимо).

### 9.24 mate-sensors-applet → «Барометр» (barometr) — М4, S
- **Был:** апплет датчиков: температуры/вентиляторы/напряжения через libsensors, hddtemp, nvme.
- **Задача:** чтение `/sys/class/hwmon` напрямую (pure Rust, без libsensors), NVMe-температура через ioctl (v2), отображение в лавке (текст/иконки), пороги → вестник, конфиг датчиков (скрыть/имя/критический).
- **Риски:** обилие вариантов hwmon — парити-лист по «типовым» датчикам (CPU, GPU v2, диски v2).
- **DoD:** на тестовой машине/дампе hwmon-структуры показываются, порог вызывает уведомление.

### 9.25 libmateweather → «Вёдро» (vedro) — М4, S
- **Был:** библиотека погоды (форк libgweather): база городов/часовых поясов, METAR,Various API-провайдеры, через libsoup.
- **Задача:** pure Rust: база локаций из данных libmateweather → статический крейт `vedro-locations` (генерация `xtask`), провайдеры — reqwest к открытым API (v1: METAR-авиапогода + один JSON-сервис, ADR на выбор), типы погоды/иконки — соответствие иконкам «Лубка», кэш и офлайн-поведение.
- **Риски:** API-провайдеры меняются — трейт `WeatherProvider`, старые отключаются конфигом; лимиты запросов.
- **DoD:** запрос погоды для 3 городов с кэшем, иконка/текст — в апплете самоделок; недоступная сеть — вежливый кэш.

### 9.26 mozo → «Буфетчик» (bufetchik) — М4, S
- **Был:** редактор меню (Python, форк alacarte): дерево меню, добавление/скрытие элементов, новый элемент.
- **Задача:** Rust-GUI на traktir v1: дерево (Genlist), свойства элемента (.desktop через svetlitsa-xdg), скрытие/показ (NotShowIn/Hidden по спеке), создание .desktop, отмена изменений (backup .menu).
- **Решения:** правка .menu только через трактир-API (валидность гарантирована).
- **Риски:** мало; главное — не сломать меню пользователя (обязательный бэкап-тест).
- **DoD:** создание/скрытие элемента отражается в меню лавки после reload.

### 9.27 mate-netbook → «Лежанка» (lezanka) — М4, S
- **Был:** утилиты малых экранов: maximus — авто-максимизация окон, диалог настроек.
- **Задача (переписана 21.11.2026, решение владельца):** забота компонента — «на маленьком экране
  должно быть удобно», а не «авто-максимизация». Состав:
  1. **Складывание приложений в стол:** одно приложение — один стол, свёрнутые приложения не
     захламляют переключатель (данные — `org.svetlitsa.Session`).
  2. **Панель-переключатель:** компактный режим лавки (иконки вместо заголовков) — состояние,
     синхронизированное с лежанкой, а не отдельная правка конфига лавки.
  3. **Поведение окон на малом экране:** авто-максимизация по списку исключений — только часть; плюс
     запрет окон меньше размера вывода, переполнение заголовка, подсказка «вернуть обычный режим».
  Механизм — события композитора (`xdg_toplevel` state, `configure`), X-событий нет.
- **Риски:** гонки с ручной максимизацией — ADR на поведение.
- **DoD:** включённая лежанка максимизирует новые окна, исключение (класс окна из списка) не максимизируется.

### 9.28 mate-wayland-session → «Новоселье» (novoselye) — М5, L
- **Был:** обёртка Wayland-сеанса MATE (сторонние композиторы).
- **Задача (после ADR-0019):** композитор уехал в М2, поэтому «Новоселье» — про **доводку сеанса**, а не про переезд на Wayland: порядок запуска и остановки компонентов, переменные окружения (`WAYLAND_DISPLAY`, `XDG_CURRENT_DESKTOP=Svetlitsa`), восстановление после падения композитора, бэкенд порталов freedesktop (М5, 4 интерфейса), проверка всех приложений на `Ecore_Wl2`, слои-панель (lavka как layer-shell-клиент — по ADR). Собственный композитор на smithay (выводы/режимы, XdgShell, софт-композитор, XWayland) — **пост-1.0 эпик**, вне релиза «Ярмарка» (ADR-0007). Плюс **бэкенд порталов freedesktop** (см. М5): четыре интерфейса минимум.
- **Решения:** `wm-core` как отдельный крейт **из 1.x убран**: после переноса композитора за 1.0 у него не осталось второго потребителя, а крейт-абстракция с одним потребителем — спекуляция. Логика фокуса/привязок живёт внутри `starshina` за внутренними трейтами; при старте пост-1.0 композитора она выносится в `wm-core` (ADR-0008). Требование «проектировать starshina с расчётом на wm-core» из М2 снято.
- **Риски:** smithay развивается — фиксировать версию в ADR; EFL-Wayland баги — план B: ранние smoke-прогоны в М4 уже под обоими бэкендами EFL; **отсутствие портал-бэкенда — не «полировка», а неработающие сторонние приложения в сеансе** (выбор файла, скрытие окна, обои).
- **DoD:** сеанс novoselye запускает лавку/вестник/бересту/морзянку на `starshina`, скриншоты, переключение столов, выход через ключника, падение композитора не утаскивает за собой данные пользователя (окна перезапускаются).

### 9.29 Не портируются
- `mate-desktop.org` (сайт) — проекту хватит страницы в README/сайте Светлицы (М5).
- `mate-wiki` (HTML) — документация живёт в `docs/` монорепо.

Внешние репозитории, проверенные по клону (детали и `HEAD` — [`docs/analysis/externals/reestr.md`](analysis/externals/reestr.md), ADR-0020):

- `gxneur` (RussianFedora) — **не портируется**: рабочее дерево 3 866 байта (spec + `sources` с md5 от
  tarball + пустой README), `HEAD` 2012-08-30, файла лицензии нет, `GPLv2` заявлено только в spec; сам
  аплет — обёртка над X Neural Switcher, то есть X-события и XKB-состояние процесса. Функция делится
  между композитором (переключение) и «Букварём» (модель, индикатор).
- `conky` — **не портируется как порт** (пост-MVP, механика в образец): 51 495 строк C++ в `src/`,
  Wayland-сборка есть, но выключена по умолчанию (`BUILD_WAYLAND=false`). Заботу «часы/монитор на
  обоях» закрывают слои `starshina` + апплеты «Самоделок».
- `parcellite` — **не портируется** (GPL-3.0, Xlib + keybinder): 7 300 строк C, из них переносится
  только модель истории и фильтров. Менеджер буфера — новое поле контракта, см. 9.31.
- `NetworkManager` — **не портируется** (GPL-2.0+ демон, 665 555 строк C): это системный демон, мы
  пишем D-Bus-клиента и секрет-агент (9.5), а не свою сетевую службу.

### 9.30 Наследие разбора COSMIC: где контракт расходится и с какой версии начинаем

Разбор COSMIC DE (`docs/analysis/cosmic/`: `reestr.md` с `HEAD` на каждую строку, `sravnenie.md` —
28 компонентов карты) дал десять мест, где их решение и наш контракт расходятся. **Правило конфликта
(12.16): пока за основу берётся COSMIC, позиция помечается `MVP по COSMIC` и ведётся в парити-листе
как незакрытая.** Отказ от космической версии в пользу MATE-паритета — решение владельца, оно
оформляется ADR, а не молчанием.

и GPL-3-ный код в инфраструктурные `svetlitsa-*` (ADR-0002).

### 9.31 Вне MATE → «Памятка» (pamyatka) — М3, S
- **Был:** ничего. В MATE менеджером буфера обмена считался сам X11 (selection-владение), а историю
  держали сторонние утилиты. На Wayland механизма-оригинала нет: буфер живёт у композитора, и
  без клиента `zwlr-data-control` история невозможна в принципе (ADR-0021).
- **Задача:** собственный менеджер буфера: история записей текста (и, отдельно, изображений), постоянный
  подсписок («закреплённые»), вызов по глобальной привязке композитора, меню выбора из лавки. Образец
  по модели, а не по коду: `parcellite` (GPL-3.0, 7 300 строк C) — список настроек одной таблицей,
  лимит истории, фильтры мусора (см. [`analysis/externals/parcellite.md`](analysis/externals/parcellite.md)).
- **Решения:**
  - **Привязка — у композитора:** `starshina` регистрирует горячую клавишу и вызывает окно «Памятки»;
    `keybinder`/`XGrabKey` не переносятся.
  - **Приватность — часть контракта, а не настройка:** лимит записей, выключение истории на время,
    «не сохранять это поле» для окна ввода пароля. Механизма «поле с флагом секретности» в
    `zwlr-data-control` нет, поэтому правило формулируется честно: **клиент, который не хочет попасть
    в историю, должен не попадать в буфер** (внешний офер с `offer` без `finish`), а «Памятка» не
    обязана хранить записи, помеченные как конфиденциальные по согласованному MIME-свойству. Если
    протокол этого не даёт — ограничение записывается в 12.x, а не замалчивается.
  - **Секреты не пересекаются:** пароли NetworkManager (9.5) и секреты `svetlitsa-config` не попадают
    в историю и в журналы.
  - **Поведение без протокола:** если композитор не отдал `zwlr-data-control` (чужой композитор,
    старая сборка), «Памятка» не запускается молча — она показывает причину и не притворяется работой.
- **Риски:** `zwlr-data-control` реализован у композиторов по-разному (у нашего — полный контроль, но
  проверять надо на `cage`/`weston` в М2); история буфера — это приватные данные пользователя на диске,
  каталог `0700`/файл `0600` и отсутствие синхронизации обязательны.
- **DoD:** smoke: скопировано два значения → по привязке открыт список → выбор второго вставлен в
  целевое окно; закреплённая запись переживает перезапуск; «не сохранять» выключает запись; файл
  истории лежит в каталоге сеанса и не читается из `svetlitsa-config`. Лист парити —
  [`docs/parity/pamyatka.md`](docs/parity/pamyatka.md) (нулевой: C-оригинала нет, ТЗ 5.1).

## 10. Проверка и приёмка

### 10.1 Тесты без дисплея
- Логика (трактир, узелок-core, счёты, vedro, izba-миниатюры, конфиги, миграция) — unit-тесты в крейтах; миграция — на дампах-фикстурах (`tests/fixtures/mate-dconf/*.dump`).

### 10.2 Тесты с дисплеем
- Всё UI-проверяемое гоняется под **headless Wayland-композитором** (`cage` или `weston --headless`, а с М2 — наш `starshina`; сценарии `scripts/smoke/*.sh`): запуск компонента, взаимодействие, завершение. `Xvfb` из ворот убран (ADR-0016), `xtask ci --doctor` ищет композитор и `wayland-scanner`.
- **Чем жмём (Q34, переписано под Wayland):** `xdotool`/`xwd`/`import` не используются — они говорят по X11. Ввод в smoke — протокол `virtual-keyboard-unstable-v1` (и мышиный аналог) на стороне композитора, тонкий тестер `svetlitsa-input`; снимок — **собственный путь захвата `starshina`** (10.3). Свой полный «xdotool-эквивалент» не пишем: нужен ровно минимум, который требует сценарий (нажать клавишу, двинуть курсор, найти окно). Вызов только из `xtask smoke`, из компонентов — никак. AT-SPI/dogtail-управления нет: его нет в EFL (12.8). `xtask ci --doctor` проверяет композитор и `wayland-scanner`; `xdotool`/`import` в контейнер не ставятся.
- **Ожидания — поллинг, а не `sleep`:** появления окна ждём по списку `org.svetlitsa.Session` (или по событию `xdg_toplevel` map) с таймаутом. Слепые `sleep` на общей машине (ADR-0003) дают ночной флак, а флакучие ворота перестают быть воротами.
- **Демо-клиент окон `svetlitsa-demo` (контракт, Q42):** app-id `xdg_toplevel` = `svetlitsa-demo`, заголовок `svetlitsa-demo:<роль>`, CLI ровно под сценарии — `--windows N` (10.5) и `--tray` (9.7); окно ищется по списку окон сеанса (`org.svetlitsa.Session`) и по `xdg_toplevel` с этим app-id, ждётся поллингом. Флагов «на будущее» нет; правка крейта ломает смоук и идёт через те же ворота. Контракт — README крейта.
- WM/сессия — полный smoke-сценарий сеанса (см. DoD М2/М4/М5).

### 10.3 Скриншоты и три контура проверки

- **Контур итерации (внутри `xtask ci`, быстрый):** unit-тесты + запуск окна компонента + **один** скриншот 1920×1080 + проверка «темы не серая».
- **Контур закрытия компонента (DoD 6.9):** полный набор ракурсов — **1024×768 и 1920×1080**, все сценарии smoke компонента.
- **Контур «толоки» (полная сборка, оба smoke-сеанса, RSS-прогоны, бенчи, пиксельные эталоны) исполняется по требованию (Q46):** на закрытии компонента (это М1 и далее) и вокруг контрольных точек, а не по cron. Постоянный прогон включается по факту, а не по календарю: трей + демо-клиент собраны и RSS-сценарий реально запускается. Формула прогона: подъём из golden image → набор 10.3/10.5 → артефакты в канон с привязкой sha канона и id образа → выключение. Побочный плюс: контейнер поднимается из golden-образа на хосте ворот и не зависит от чужих сессий, требование «спокойной машины» для RSS (10.5) выполняется в любое время суток.
- `xtask screenshot --out artifacts/<компонент>/` — снимок через захват композитора (PNG) до/после действий; `xwd`/`import` в воротах нет (ADR-0016).
- **«Серая тема» — механическая провалка ворот, а не мнение:** в снимке обязаны присутствовать токены темы (фон «Лубка», цвет контура) и не менее 10 различных цветов; чистый серый/дефолт Elementary = красный прогон.
- Пиксельные эталоны с допуском (SSIM/средняя дельта) — только в «толоке» и только после стабилизации темы «Лубок»: эталоны, которые перетирают каждую неделю, перестают быть проверкой.
- Прочие визуальные критерии брака: обрезанный текст, наложение элементов, нечитаемые шрифты.

### 10.4 Smoke сессии (интегральные)
- `xtask smoke session` (имя `session-x11` упразднено вместе с X11-веткой) — старт ключника под headless-композитором, порядок М2/М4-компонентов, скриншоты, чистое завершение кода 0.
- «Толока» (nightly CI): полная сборка + оба smoke + пуш скриншотов в артефакты.

### 10.5 Производительность и память
- Бенчи: morzyanka-вывод, ambar-сканирование 10 тыс. файлов, лавка с 30 апплетами — замеры в `benches/`, пороги в парити-листах.
- Утечки: RSS-прогоны — **только в ночной «толоке»** (30): на общей машине днём они тонут в шуме чужих процессов и дают красные прогоны без вины кода.
- **Сценарий RSS-прогона фиксирован (Q38):** 20 открытых окон + 50 переключений рабочих столов + 10 открытий меню; метрика — `RSS(10 мин) − RSS(1 мин)`, порог **+2% за 9 минут**. Окна для сценария создаёт **демо-клиент окон** — тот же, что нужен smoke-прогону трея (9.7): один артефакт закрывает обе задачи.

## 12. Приложение Б. Честные ограничения и компромиссы

1. **Rust-биндинги EFL строятся сами.** Официальных нет; крейт `efl` на crates.io (0.3.0, 2024) недостаточен. `svetlitsa-efl` — это самостоятельный, самый ответственный крейт проекта; его парити-лист живёт отдельно и расширяется по мере нужд компонентов (без «на всякий случай»).
2. **Часть GLib-мира остаётся.** GIO/GVFS и poppler работают как C-зависимости через FFI (allowlist 3.3). Полный уход от glib — отдельный эпик после М5, не входит в обещание 1.0.
3. **Wayland — единственная платформа (переписано 21.11.2026, ADR-0016).** X11-сеанса, Xorg-сессии и X11-ветки портов в 1.0 нет; рабочий Wayland-сеанс — не М5, а М2 (композитор `starshina`). Все упоминания X11 в ТЗ означают механизм оригинала MATE.
4. **Темы marco не переносятся автоматически** — «Светлица» делает собственную тему «Лубок»; парсер marco-тем — backlog с ADR.
5. **Форматы, которые нельзя честно портировать** (rar — только чтение; проприетарные кодеки) фиксируются в парити-листах как «чтение/нет».
6. **Объём.** 28 компонентов — многолетний объём работы; майлстоуны задают порядок и готовность, а не календарь. Агент обязан работать итерациями по 6.8 и не «замыливать» парити-листы ради скорости.
7. **Имена.** Русская система имён (7.2) — часть контракта: латиница в коде, русские названия в UI; пересмотр имени компонента после его порта — только через ADR с миграцией (крейт, бинарь, D-Bus, конфиги).
8. **Скринридеров (AT-SPI) в 1.0 нет.** Доступность 1.0 — клавиатура, контраст «Мезени», отключаемые анимации, масштабируемые шрифты (7.3). Обещать поддержку скринридеров на EFL — значит обещать несуществующее.
9. **Языки 1.0 — русский и английский.** `po/` монорепо, русские каталоги конвертируются из MATE; остальные языки MATE в 1.0 не обещаются.
10. **Крейты и имена не публикуются до 1.0** — резервирование имён `izba`/`lavka`/`traktir`/… на crates.io откладывается до 1.0 и делается только через ADR.
11. **IME (ibus) — по факту того, что умеет `Ecore_IMF` на Wayland (`zwp-text-input-v3`), xim недоступен в принципе.** Если путь не работает, ограничение записывается здесь и в 4.4, а не замалчивается; русская раскладка при этом работает через `bukvar` (xkb), а не через IME.
12. **Печать из бересты и свитка в 1.0 недоступна.** CUPS, ppd, диалог и предпросмотр — объём размером с компонент; возврат — отдельная спецификация после 1.0.
13. **XEmbed-трея в 1.0 нет** (переписано 21.11.2026): XEmbed поднимает X-окно, а X-сеанса нет. Трей = `org.kde.StatusNotifierItem`/`StatusNotifierWatcher` и ничего больше (9.7). Лавка как панель висит на `wlr-layer-shell`, и композитор с этим протоколом — наш (ADR-0019), то есть внешний риск «а вдруг композитор не даёт» снят.
14. **Собственный композитор — обещание 1.0** (переписано 21.11.2026, ADR-0019 вместо ADR-0007): `starshina` на smithay строится в М2, потому что на Wayland без композитора нельзя показать ни одного окна. Это самая дорогая часть плана: оценка М2 `XL` дана до переезда композитора и уточняется после первой итерации М2.
15. **Редактора сетевых соединений в 1.0 нет, просмотр и подключение — есть** (уточнено 21.11.2026).
    Граница заботы: список сетей, подключение/отключение, пароль на точку, состояние «не подключено» —
    это наш клиент NetworkManager (9.5, секрет-агент там же); создание мостов, VPN, мобильный, 
    редактирование конфигурации соединений — `nmcli` или сторонние приложения. Модуль `network` из
    `mate-control-center` в сходку не входит (9.20).
16. **Правило конфликта с COSMIC (разбор `docs/analysis/cosmic/`).** Где их решение расходится с нашим контрактом, за основу пока берётся COSMIC, а позиция ведётся в парити-листе как незакрытая с пометкой `MVP по COSMIC` (перечень — 9.30). Паритет MATE от этого контрактом быть не перестаёт: правило отвечает на вопрос «с какой версии начинаем», а не «что считаем готовым».
17. **X11-приложения официально не поддерживаются** (ADR-0016, ADR-0017). Приложение без Wayland-порта
    заработает в сеансе «Светлицы» только через XWayland, а XWayland не входит ни в один DoD и ни в одну
    сборку сеанса. Следствие для трея: X11-приложение, умеющее только XEmbed, в трей не встанет. Это не
    «временно сломано», а граница 1.0; вернуть поддержку можно только ADR, возвращающим X11-стек.
18. **PulseAudio-стек не поддерживается** (ADR-0022): звук — PipeWire + WirePlumber, привязка одна
    (9.15). Машина без PipeWire звуком «Светлицы» не пользуется; отдельной PulseAudio-ветки граммофона
    нет, и «v1 на PulseAudio, v2 на PipeWire» из плана убрано.
19. **Минимум зависимостей — это правило белого списка, а не «нулевой C».** На подсистему — одна
    FFI-привязка (3.3); зависимость появляется вместе с задачей, проверкой `LICENSE` и строкой в
    `docs/licenses.csv` (ADR-0002). Кандидаты из разборов (в том числе семь из COSMIC) не считаются
    зависимостями, пока под них не открыта задача.
20. **Только musl, только x86_64, только openrc/BusyBox; сборка — только в Docker на Alpine** (ADR-0023).
    glibc, 32-битных сборок и multilib нет; systemd, journald и `logind` в образе нет — сиды, питание и
    блокировка идут от собственного слоя поверх `seatd`, `letopis` v1 не читает системные журналы.
    Локаль и перекодирование не берутся из libc. Доказательством сборки считается прогон в контейнере
    на Alpine, а не «у меня на хосте собралось»; хостом может быть Linux или macOS (ADR-0023,
    поправка 1), но проверки, которые macOS не выполняет, доказательством не объявляются.
